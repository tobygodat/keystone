# Checkpoints and Restore to here (TOB-58)

In a git folder, each turn's end saves the session's files as a checkpoint, and Restore to here puts them back and continues the conversation from that turn in a fork. In a folder outside any repository, the latest turn's control says that checkpoints need one.

## Entry points

- The Restore to here button (`restore-<row>`, a counter-clockwise arrow) under each turn's last reply, with how many files that turn changed beside it (`checkpoint-files-<row>`) when it changed any. That count is a button that opens the turn's diff (see [diff](diff.md)).
- The command palette: "Transcript: restore to the focused turn", or Ctrl+Shift+Z, with the transcript focused on that reply.

## Expected behaviour

- As a turn ends, Keystone builds a tree of the working tree's tracked and untracked files without ignored ones, in an index file of its own in the repository's git folder (`GIT_INDEX_FILE`), and saves it as a commit named only by `refs/keystone/checkpoints/<store>/<session>/<turn>`. `<store>` is a random name the workspace keeps in its database, so two Keystone workspaces using one repository never share refs, and a saved ref is never replaced. Turns are numbered per session from 1. The user's index file, HEAD, branches and stash are never written. A worktree session checkpoints its own worktree; the refs are shared by the repository.
- Untracked nested repositories and untracked files over 20 MB stay out of checkpoints. The checkpoint records what it left out, and a restore leaves those paths as they are and lists them. In a sparse checkout, files outside the cone stay off disk.
- The file count compares the tree the turn started from, read before its first message went, with the one it ended with. A message sent during a turn that becomes the next turn waits until the ended turn's checkpoint is saved; that turn starts from it.
- Each session keeps its newest 50 checkpoints; older refs are deleted as each new one is saved. Debug builds take `KEYSTONE_TEST_CHECKPOINT_KEEP` for fewer. Each save also deletes every checkpoint ref saved more than 30 days ago in that repository, in any workspace's store and any session, `before-restore` included, so sessions nobody uses and workspaces that are gone do not keep theirs forever. A ref saved again meanwhile stays. Keystone deletes only refs; git's own gc frees what they held.
- Restore to here asks first ("Restore to here": "Files go back to this turn, and the conversation continues in a fork.", Restore). Restore is refused with "A turn is running here. Stop it first." while any session's turn runs, a held follow-up waits, or a checkpoint is being saved in the same repository. It runs on a thread of its own, so it holds no provider's sessions elsewhere. While it runs ("Restoring…"), a message to any session in that repository is not sent ("Not sent. Files are being restored."), and a launched session's result waits. Cancel or Escape stops it: the git command running is killed with what it started, every file is put back, and the dialog closes. Meanwhile Restore is off and a press outside the dialog does nothing.
- A restore first saves the working tree as `<store>/<session>/before-restore`. Git then converts the files the checkpoint has that differ into `keystone-restore-<pid>-<n>/` in the git folder before any file of the working tree changes, so a filter that hangs or fails there changes nothing. A path only the deletes free, or one a case-only rename makes look taken, is converted as it is placed, and a failure then is undone like any other. The files are then moved into place, each one they replace moved aside, and files created since are deleted, with folders they leave empty. No untracked file ignored by the checkpoint's .gitignore rules or the current ones is read, written or deleted; a tracked file is restored even when a rule now matches it, as git treats it. A file modified (by its modified time) after the restore read the working tree, a folder standing where a file goes, and anything inside a nested repository are left as they are and listed. A file that something else edits or makes while the fork opens is kept if the restore is undone, and its original stays in the restore's folder. Keystone's own ref updates run without the user's git hooks.
- A restore is all or nothing. The files stay only once the fork opens. If anything fails, or the fork can't open, every file is moved back, the dialog says why, and no fork is made. If a file can't be moved back, or one was edited while the fork opened (the edit stays), the dialog names the folder that holds the originals. This holds while Keystone runs: if it is killed mid-restore, the working tree stays as it was then, and the files it replaced are in that folder's `aside/` and in `before-restore`. After relaunch the session shows "A restore didn't finish." (`restore-unfinished`) with **Put files back** (`put-back`), and a new restore is refused with "Put files back first." A folder holding such files is never expired; one left with only converted copies goes after 30 days. Quitting during a restore cancels it first. Submodules and nested repositories are not touched. Paths it had to leave as they are (a folder or ignored file where the checkpoint has a file, a nested repository) are listed in the fork it opens: "Not restored: …", with the first three paths and how many more.
- With the files in place, the conversation forks from that reply as Fork from here does (see [fork](fork.md)), so the source session and its later turns stay as they were. "Not restored: …" goes in that fork, never in the source. The restore itself keeps every checkpoint.
- A session whose folder is in no repository shows the button only on the latest turn's last reply, with the tooltip "Checkpoints need a git repository."; pressing it does nothing more. The palette command, which has no tooltip, says the same on the app's error line. Neither adds a line to the conversation.
- Line endings follow git's own conversion: with `core.autocrlf` or `eol` attributes, a restored file has the line endings `git checkout` would give it.

## Native journey

Use a fixture repository with a commit, a staged file, a stash and ignored files, and the scripted Claude in store mode (`KEYSTONE_FAKE_CLAUDE_STORE=1`). Each line of a prompt reading `write <path>: <text>` or `delete <path>` makes the fake edit its working directory before replying. Give a session two turns that write, edit and delete files, then press Restore to here on turn one's reply and confirm. Check:

- `git for-each-ref refs/keystone` lists `refs/keystone/checkpoints/<store>/<session>/1` and `/2`, and `before-restore` after the restore.
- The working tree's files hash the same as `git ls-tree -r refs/keystone/checkpoints/<store>/<session>/1`, files created in turn two are gone, and ignored files are byte-for-byte unchanged.
- `.git/index`, `git rev-parse HEAD` and `git stash list` are unchanged.
- A new tab holds the fork with turn one only, linked by `forked_from`.
- With a turn held mid-reply (`KEYSTONE_FAKE_CLAUDE_DELAY_MS`), Restore is refused and no file changes.
- With `KEYSTONE_TEST_CHECKPOINT_KEEP=2`, a third turn removes `/1`.
- A ref of another store dated 31 days back (`GIT_COMMITTER_DATE`) is gone after the next turn's save; one dated 29 days back stays.
- With a smudge filter that hangs on `*.txt` (`.git/info/attributes`), Restore shows "Restoring…"; Cancel closes the dialog, every file hashes as before, no `keystone-restore-*` folder is left, and the next message sends.
- With a smudge filter that fails (`filter.<name>.required`), Restore shows git's error in the dialog and every file hashes as before.
- With the workspace database held by another writer (an open `BEGIN EXCLUSIVE` on the live database), the fork can't open: the dialog shows why, every file hashes as before, and there is still one session.
- Outside git, pressing the control adds no conversation error.
