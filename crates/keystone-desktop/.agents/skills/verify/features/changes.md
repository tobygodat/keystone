# Changes

Stage, commit and push the selected session's repository from a Changes view, with the user's own `git`, and create a pull request with the user's own `gh`. There is no diff view, and Keystone never holds a GitHub token.

## Sub-features

- `changes-surface` is a layout component like Files: at most one per project layout, beside a conversation, as a tab with Files, or a fitted tab in a narrow window. Its tab reads "Changes · N" once N files are changed.
- `changes-root` follows the selected session's recorded folder (a worktree session's worktree), else the current project. git runs in that folder's top level. A folder outside any repository shows git's own message.
- `changes-list` groups Conflicts, Staged, Changes and Untracked with counts. A file with staged and unstaged edits is listed in both. Rows show git's one-letter state (`?` untracked, `!` conflicted), the name and its folder.
- `changes-stage` stages (`git add --all`) or unstages (`git restore --staged`, or `git rm --cached` before the first commit) one row, or a whole group from its header. Staging a conflicted row marks it resolved, and is refused while the file still has `<<<<<<<` or `>>>>>>>` lines; Stage all on a header never touches conflicts.
- `changes-open` opens a row in `$VISUAL`, `$EDITOR` or `xdg-open` (`open` on macOS), as Files does. `changes-copy-path` copies its absolute path.
- `changes-commit` runs `git commit --file=-` with the user's hooks and signing. Success clears the message. Failure shows git's and the hooks' output and keeps the message.
- `changes-draft` saves the unfinished message per folder 250 ms after typing stops, and on Quit or window close, and restores it after a restart.
- `changes-push` pushes the branch shown with `git push --no-follow-tags --recurse-submodules=no [--set-upstream] -- <remote> refs/heads/<branch>:refs/heads/<branch>`. The refspec is spelled out, so a configured push refspec, mirror or `push.default=matching` never reaches another branch, tags and submodules are never pushed with it, and it never forces. The remote is the branch's `pushRemote`, then `remote.pushDefault`, its upstream's remote, `origin`, or the only remote. `--set-upstream` is added when the branch has no upstream, or when its upstream is another branch (such as `origin/main` it was started from) and no push remote is configured; a triangular setup keeps its upstream. The row under the branch shows the upstream (`changes-upstream`; "Not pushed" before the branch is published, and empty for a branch published to a push remote with no upstream) and `↑ahead ↓behind` against the upstream (`changes-sync`) when there is one and either count is non-zero. Push is enabled on any branch and disabled on a detached HEAD. A mirror remote (`remote.<name>.mirror`) refuses the explicit refspec, so Push shows git's error there. A rejected push shows "Push rejected." with git's output. With no remote (`changes-hint-no-remote`), or several and none chosen (`changes-hint-unclear-remote`), it shows the command to run.
- `changes-create-pr` is enabled once a session is selected and the branch is published: with a push remote configured (`branch.<b>.pushRemote` or `remote.pushDefault`), that remote has a branch of the same name (read through the remote's fetch refspecs; a remote that fetches no copy of the branch counts as published and gh reports if it is not); otherwise the upstream is the branch of the same name and still on the remote (a pruned upstream is not published). With commits not yet on it, it asks for a push first. With no gh found on PATH or in the usual install folders (`/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin`, `~/.local/bin` and others) (`changes-hint-gh-missing`) it shows `gh auth login` and opens no form. Otherwise it shows a form: title (the session's title to start), description, base (the remote's default branch, from `refs/remotes/<remote>/HEAD`, else empty so gh picks) and a Draft switch. Create first checks that the branch the form was opened for is still checked out (by its full ref, so a tag of the same name doesn't matter), then runs `gh pr create --title <title> --body-file - [--base <base>] [--draft]` with the description on stdin, in the repository's top folder, with no terminal, prompts disabled and `GH_REPO` dropped. The new pull request, or the one gh says the branch already has, is saved on the session the form was opened for (`pull_request` with `number` and `url` in the session row), even if the window closed meanwhile, and shows as `#N` in the top bar (`session-pull-request`), which opens it in the browser. A new pull request shows no notice; one gh says already exists shows "Already open: #N.". The palette's **Copy pull request link** (Ctrl+Alt+C) copies its URL. gh exiting 4 (no login for the repository's host) shows `gh auth login` (`changes-hint-gh-signed-out`) and keeps the form; any other failure shows gh's output and keeps the form. Cancel is disabled while gh creates. Selecting another session closes an idle form; a form gh is working for stays until gh answers. A session handed off to another provider keeps the pull request.
- `changes-refresh` re-reads status when the view opens or its folder changes, when the window regains focus, after an agent's file-change item or turn ends in that folder, after each stage or commit, and from the refresh button. Reads use `--no-optional-locks`.

## How to get to it (user POV)

- Press Ctrl+Shift+G, or choose **Toggle changes** in the command palette. With no Changes view it opens one as a tab with Files when Files is open, else 300 px wide right of the conversation, and focuses the message box. With one unfocused or behind another tab, it brings it forward. With focus inside it, it closes it.
- Click **+** on a tab strip and choose **Changes**. A fitted window draws no **+**.
- Click a row's + or −, or highlight a row and press Space. Enter or a click opens the file. Ctrl+Shift+C copies the highlighted row's path.
- Type a message and press Ctrl+Enter anywhere in the view, or click **Commit**. Ctrl+Enter in Changes never sends the composer.
- Click **Push**. Click the pull request button beside it, fill the form, and press Ctrl+Enter or click **Create**; **Cancel** closes the form.

## Driving it with keystone-verify

Preconditions: a disposable git repository as `KEYSTONE_PROJECT_DIR` with local `user.name`, `user.email`, `commit.gpgsign=false` and `core.hooksPath=.git/hooks`, so the run never uses the host's hooks or signing. Use the scripted Claude through a wrapper that sets a scratch `CLAUDE_CONFIG_DIR`.

Named elements: `changes-message`, `changes-commit`, `changes-branch`, `changes-upstream`, `changes-sync`, `changes-push`, `changes-create-pr`, `changes-pr-form`, `changes-pr-title`, `changes-pr-body`, `changes-pr-base`, `changes-pr-draft`, `changes-pr-create`, `changes-pr-cancel`, `changes-hint-command`, `changes-hint-copy`, `changes-hint-<case>` (`gh-missing`, `gh-signed-out`, `no-remote`, `unclear-remote`), `changes-notice-title`, `session-pull-request`, `changes-refresh`, `changes-notice`, `changes-notice-dismiss`, `changes-output`, `changes-empty`, `changes-unavailable`, `changes-list-row-N`, `changes-all-<group>` and `changes-stage-<group>-<path>` with group `staged`, `unstaged`, `untracked` or `conflicted`. The set of `changes-stage-*` names is the drawn list, so compare it with `git status --porcelain`.

The journey that proves this feature: create a session, open Changes from **+** (1280) or Ctrl+Shift+G (720) and from the palette, compare the list with `git status --porcelain`, stage one file, commit "verify commit" and check `git log -1`, install a failing pre-commit hook and check its output and the kept message, read `commit_drafts` with `workspace`, then Quit and relaunch and check the restored view and draft.

For push and pull requests: use a temporary bare repository as `origin`, and a stand-in `gh` that records its arguments and stdin and prints a fixture pull request link, first on `PATH` (pass `PATH` in `start`'s `env`) with a disposable `GH_CONFIG_DIR`, so the run never reaches GitHub or the user's gh login. Keystone also looks for gh in `/usr/bin`, `/usr/local/bin` and folders under `HOME` (the run's empty `HOME`), so on a machine with gh in `/usr/bin` the missing state can't be shown this way. Push a new branch and check the bare repository has it. Commit to the bare repository from another clone, commit locally and push: the rejection shows and the bare repository keeps the other commit. Create a pull request from the form and check the recorded arguments and body, `session-pull-request`, and `pull_request` in `workspace`. Make the stand-in exit 4 for `changes-hint-gh-signed-out`, then remove it for `changes-hint-gh-missing`.
