# Integrations

List the MCP servers, skills and plugins each provider account loads for the window's project, read from the providers' own files, with what running sessions in that project last reported about each server, and change them: add, edit, switch and remove MCP servers, switch plugins, and add and remove skill folders.

## Sub-features

- `integrations-read` reads, per account (each provider's default and every added one) and the window's project: Claude's `.claude.json` (user `mcpServers`, local `projects["<git root>"].mcpServers`, `disabledMcpServers`, `disabledMcpjsonServers`), `.mcp.json` in the project and each folder above it up to its git root, `enabledPlugins` in `<config>/settings.json`, `.claude/settings.json` and `.claude/settings.local.json` with versions from `plugins/installed_plugins.json`, and skills in `<config>/skills`, `.claude/skills` and each loaded plugin's `skills` folder (named `plugin:skill`); Codex's `config.toml` (`[mcp_servers]`, `[plugins]`, `[[skills.config]]` and project trust), `.codex/config.toml` in the project and the folders above it up to the git root (shown "Project not trusted by Codex" until the nearest `[projects]` entry trusts it), and skills in `$CODEX_HOME/skills`, `~/.agents/skills`, `.agents/skills`, `.codex/skills` and each enabled plugin's highest cached version. The account's own files are never read a second time as the project's when the git root is the user's home. Hidden skill folders such as Codex's `.system` are skipped. Layouts are in `docs/research/integrations-probe.md`.
- `integrations-overrides` marks a server or plugin declared again at a stronger scope (local over project over user, and the nearest file at one scope) "Overridden by <scope> scope"; it shows no status.
- `integrations-secrets` keeps a stdio server's command (its first word only, if a whole command line was pasted there) and only the number of its arguments, the names of its env variables and headers, and only a URL's scheme, host and port (`/…` when it goes on; a URL that does not parse shows `•••`). Provider error text is never kept. A file that cannot be parsed is listed under the groups with the parser's message, never its contents.
- `integrations-status` shows each server's status from the newest report of a session whose process is still running, in the window's project folder itself: Claude's `system/init` `mcp_servers` and Codex's `mcpServer/startupStatus/updated`, without Keystone's own `keystone` and `keystone_ui` servers. A session's report replaces its last one, and a session that stops takes its report with it. An untrusted or overridden declaration gets no status. A server no file declares, such as a plugin's, is listed as reported by a running session. Before any running session reports, a server shows "Not running".
- `integrations-refresh` reads the files again with Refresh, which is off while a read or a change is under way. Opening the section reads them each time, and only the newest read fills the page.
- `integrations-change` makes each change through the provider's own CLI where one covers it, run as that account (its `CLAUDE_CONFIG_DIR` or `CODEX_HOME`) in the project folder: `claude mcp add-json -s <scope>` and `claude mcp remove -s <scope>` (an edit is remove, then add-json with the merged definition, and add-json of the old one if that fails), `claude plugin enable|disable -s <scope>`, `codex mcp add` and `codex mcp remove` at user scope. Everything else is a direct edit that keeps the rest of the file: `enabled = false` (or its removal) in a Codex `[mcp_servers.<name>]` or `enabled` in `[plugins."<id>"]` through `toml_edit`, so comments stay; Codex project servers and every Codex edit in `config.toml` or `.codex/config.toml`; a Claude project server's switch as `disabledMcpjsonServers` in the project's `.claude/settings.local.json` (also read from there now); a Claude user or local server's switch as `disabledMcpServers` in an added account's `.claude.json`. The default Claude account's `.claude.json` is never edited directly: a user or local server's switch there shows disabled (`<row>-switch-claude`, tooltip "Use /mcp in Claude."), and a project server whose `.claude.json` lists it off is refused with "Use /mcp in Claude." `codex mcp add` of a name already in `config.toml` is refused before it runs, since Codex would replace that server whole. Skills are copied into `<config>/skills` or `.claude/skills` (Claude), `$CODEX_HOME/skills` or `.agents/skills` (Codex); a removed skill folder moves to the backups. A plugin's skills have no Remove, and an untrusted Codex project server has no switch.
- `integrations-conflict` compares every file a change writes, and a skill folder it removes (every file in it), with the fingerprint the shown read took (of `.claude.json`, only `mcpServers` and the window project's `mcpServers`, `disabledMcpServers` and `disabledMcpjsonServers`, since Claude rewrites the rest as it runs), and each direct edit checks again on the text it edits. A mismatch shows "Edited outside Keystone" with Review in Refresh's place, which reads again, and nothing is written or run. A change or Refresh under way holds further changes.
- `integrations-backup` copies each file a change may write to `config-backups/<time>/<path>` beside Keystone's database first, in folders only the user can read, and replaces an edited file atomically with its permissions kept (a symlinked file's target is replaced, so the link stays). If a Claude edit's add fails after its remove, the old definition is added back, and a failed restore names the backup folder. A CLI's error has every value the call passed hidden, and of each argument and command word also what follows its first `=` and the credential after `Bearer ` or `Basic `, and of each URL among them its user and password, each path segment and each query or fragment value of 8 or more characters.
- `integrations-copy` copies an MCP server or a skill folder (not a plugin's) to another account, of either provider, once. The panel under the row picks the account and scope and previews the file or folder it writes and exactly what goes there. A value that looks like a secret is shown as `••••` and left out unless its switch is on: an env or header value, `--flag=value` or the value after a `--flag` whose name has a part ending in TOKEN, KEY, SECRET, PASSWORD, PASSWD, PASS, AUTH, AUTHORIZATION, CREDENTIALS or COOKIE (not a `--no-…` switch), any of those or an argument holding a bearer or basic credential (after a colon with or without spaces, as in `Authorization:Bearer …`), an argument that is a JSON object (`--config '{…}'`) holding a string, at any depth, that is non-empty and not `${VAR}` under a key named as above or that is a secret by itself, the word of 8 or more characters after a `Bearer` word or a word ending in `:Bearer`, or after a `Basic` word that follows a word ending in `Authorization:`, or after a word ending in `Authorization:Basic` (any case, not `${VAR}` or `$VAR`, not starting with `-`), a URL with a password, a secret user or a secret path segment, or a well-known token prefix (`sk-`, `ghp_`, `github_pat_`, `glpat-`, `xoxb-`, `AKIA`…), and a URL's password, or its whole user and password when the user name is secret (left out with its `@`), secret path segments, secret query values and the secret values of a fragment written `k=v&k=v` (switch `URL`; a fragment left with none goes with its `#`). A path segment, or the user name before any `:`, never the host, is judged percent-decoded and without trailing `=`: secret when it starts as a token does, is a UUID, holds a piece between `-`, `_`, `.`, `~` and `:` of 16 or more letters and digits mixed, or is 20 or more letters, digits, `-`, `_`, `+` and `/` with a capital, a small letter and a digit, at least half of whose letters and digits are in pieces between those separators that hold both a letter and a digit, so names, model names such as `Llama-4-Scout-17B-16E-Instruct` or `Mistral-Large-Instruct-2411`, versions, dates and plain numbers are not; the URL keeps the segment as it was written. The command is split into words as a shell splits it (single and double quotes; outside quotes `\` escapes the next character and `\` before a newline joins the lines; inside double quotes `\` escapes `"`, `\`, `$` and a backtick) and its words are read as the arguments are, and any hit makes one switch, `Command`: shown, each hit's value is `••••`; left out, the hit words go (a flag with its value) with the whitespace that parts them from the rest. Every other byte of the command stays as written, and a command with no hit is copied as it is. A `${VAR}` reference is not a secret, and neither is a credential after `Bearer` or `Basic` written `$VAR`; an env, header or password value written `$VAR` still is, since Claude does not expand it. Codex can't expand any other `${…}`, so such a Claude server is refused, as is a Codex server whose literal text holds `${` (Claude would expand it), or one with `enabled_tools`, `disabled_tools` or `cwd` for Claude. A copy arrives switched on. The preview is worked out off the UI thread, and the panel closes when the accounts change under it. Copy works the preview out again just before it writes. If the server's definition or the skill folder's content no longer gives what the panel shows, nothing is written, the panel shows the new preview under "<name> changed since the preview." (`integrations-copy-changed`, while the panel is still that copy to the same account and scope and the new preview can be made, until the next Copy, another account or scope, or the panel closes), and a second Copy writes that. An edit to the rest of the source's file is not a change. A server copy writes the definition the preview holds. A skill folder is copied beside its target and hashed before it is moved into place; if it no longer has the content the preview hashed, it is discarded, nothing lands and the page shows "Edited outside Keystone". A skill's links are listed and copied as links, never followed. A Claude copy runs `claude mcp add-json`; a Codex copy appends `[mcp_servers.<name>]` to `config.toml` or `.codex/config.toml` with the rest of the file untouched, since `codex mcp add` can carry neither headers nor the other tables' comments. Between providers a server keeps its command, arguments and env, or its URL and headers; Codex's `env_vars`, `env_http_headers` and `bearer_token_env_var` become Claude's `${VAR}` references and back. Plugins say "Claude only" or "Codex only" and have no Copy. Each copy is remembered (`integration_copy/` in the database's `metadata`), and every read compares its two ends: both rows say "Out of sync with <provider> · <account>" once either changes, and the copy says "Needs <name>" while it lacks a secret left out. `URL` and `Command` count as back only when, masked, they read as the source's do masked, so every secret they held is back. These notes come before the row's own (Overridden, Project not trusted). Nothing is ever fixed automatically. A pair whose end is gone is forgotten.
- `integrations-next-start` says "Running sessions get this at their next start." after a change while a session of that account runs.

## How to get to it (user POV)

- Press Ctrl+Comma, then choose Integrations. The section lists MCP servers, then Skills, then Plugins, each with a count. A row shows the name (with Off, Overridden or Project not trusted when the provider does not use it), how it runs or its description or version, and provider · account · scope · source file (a plugin's skill names its plugin instead). A server's status sits on the right; its tooltip says when it was reported.

Each MCP server row has a switch (`<row>-switch`), Edit (`<row>-edit`) and Remove (`<row>-remove`); a plugin row a switch; a skill row Remove. The plus beside MCP servers (`integrations-add-mcp`) and Skills (`integrations-add-skill`) opens a form: account (`integrations-form-account`), scope (`integrations-form-scope`), then name, command or URL, arguments and environment (`integrations-form-name`, `-target`, `-args`, `-env`), or the skill folder (`integrations-form-folder`); `integrations-form-submit` and `integrations-form-cancel`, or Enter and Escape. Copy (`<row>-copy`) opens `integrations-copy-form` under the row: account and scope as in the add form, `integrations-copy-preview` (one line per previewed line), a switch per secret (`integrations-copy-secret-<name>`), `integrations-copy-error` when it cannot be made, `integrations-copy-changed` above the preview when the source changed since the one Copy was pressed on, then `integrations-form-submit` (Copy). A row's note is `<row>-note`. Arguments and environment are shell words, the environment as `NAME=value`. Edit fills the form from the file but hides what the list hides: each environment value as `NAME=••••`, the arguments, a URL and a command of more than one word as `••••`. A field left as `••••` keeps what the file has; typing over it replaces it.

## Driving it with keystone-verify

- `start` gives the app an empty `HOME`, and empty `CLAUDE_CONFIG_DIR` and `CODEX_HOME` unless the server inherited them, whenever `env` names none. Name fixture homes for all three (Codex reads `~/.agents/skills`), and set `KEYSTONE_FAKE_MCP_CONFIG=1` so the scripted providers report the fixture's servers. Never run this section against the real `~/.claude`, `~/.claude.json`, `~/.codex` or `~/.agents`.
- `click` `{"id":"settings-section-integrations"}`, then `wait_for` a row: `integration-<provider>-<account>-<mcp|skill|plugin>-<user|local|project>-<name>`, such as `integration-claude-default-mcp-user-fixture-ok`. A second row with the same ID within one account ends in `-2`, and so on. A status element is the row's ID plus `-status-<state>`: `not-running`, `connected`, `starting`, `failed`, `needs-sign-in`, `off`, or `none` for a server the provider does not use. Reported-only servers use scope `reported`.
- The scripted providers report every server their fixture config turns on: a stdio server whose command is `false` fails, every other one connects. Send once in a Claude and a Codex session, reopen Integrations and require `-status-connected` and `-status-failed`.
- Read `elements` and OCR the screenshots, and require a fixture secret value in neither. Put the secret in an argument, a URL path and a URL password as well as an env value.

- Set `KEYSTONE_CLAUDE_PATH` and `KEYSTONE_CODEX_PATH` to the scripted providers: their `mcp` and `plugin` commands write the fixture files as the real CLIs do, and `KEYSTONE_FAKE_ENV_RECEIPT` records each call's arguments and account folder.
- A conflict: change a fixture file from outside while the section is open, then switch a row. Require `integrations-conflict` and the file unchanged byte for byte.

## Gotchas

- Status comes only from sessions that ran in this project's folder; a session started in a subfolder is not counted. Keystone never starts a provider or an MCP server to ask, so a server shows "Not running" until a session of that account starts here, and again once every such session has stopped.
- `codex mcp add` and `codex mcp remove` rewrite every `[mcp_servers]` table: Codex 0.163.0 drops the comments inside them and writes `20` as `20.0` (probe on desk, 2026-10-25). The scripted Codex does not, so a native run cannot show this.
- Claude sends `system/init` only once a turn starts, so a server that was pending then may show "Starting" until the next turn.
