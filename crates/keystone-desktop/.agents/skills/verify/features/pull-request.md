# Pull request

The selected session's pull request as the user's own `gh` reports it: title, state, branches, review decision, checks and reviews, refreshed while it is open, with a Merge button that always asks first. Keystone never holds a GitHub token.

## Sub-features

- `pull-request-surface` is a layout component like Changes: at most one per project layout, as a side surface or a tab. It shows the selected session's pull request: the one saved on the session (TOB-52's `pull_request`), else the open one gh finds for the branch checked out in the session's folder (`gh pr view --json number,url,state`), which is then saved on the session. With none, or in a folder with no git repository or no GitHub remote, it reads "No pull request." gh runs with prompts disabled and `GH_REPO` dropped: finding a pull request runs in the session's folder, and everything addressed by the pull request's link runs there too, or in the temporary folder once the folder is gone, as a removed worktree's is. Each gh call that takes over 60 seconds is stopped, with whatever it started, and shows as a failure; a merge stopped that way may still have happened, which the next answer shows. Merges run on their own thread, so a slow poll never holds one up.
- `pull-request-report` comes from `gh pr view <url> --json title,state,isDraft,baseRefName,headRefName,headRefOid,reviewDecision,mergeStateStatus,statusCheckRollup,reviews` and `gh api --hostname <host> --paginate repos/<owner>/<repo>/pulls/<n>/comments?per_page=100`. The header shows the title (`pull-request-title`), `#N`, the state (`pull-request-state`: Open, Draft, Merged or Closed), the review decision (`pull-request-review-decision`), Conflicts when GitHub reports the merge state as DIRTY (`pull-request-conflicts`) and `head → base` (`pull-request-branches`). Checks, then reviews and comments, follow as two groups with no titles. Each check (`pull-request-check-N`) shows its mark, `workflow / name`, GitHub's own word for its state and how long it has run while running, or how long it ran once GitHub gives both ends (a commit status gives no end, so it shows no time once done); a click opens its details page. Reviews (`pull-request-review-N`, the author and Approved, Changes requested or Dismissed, then any text) and line comments (`pull-request-comment-N`, `path:line` and author) follow; a comment opens its file, under the top folder of the repository holding the session's folder, in `$VISUAL`, `$EDITOR` or the system opener (`xdg-open`, or `open` on macOS), as Files does, also for a restored report gh has not been asked about since. The last report is saved on the session (`pull_request_watch` in the session row) and shown again after a restart.
- `pull-request-poll` asks gh again 30 seconds after the last ask while any window draws the surface for that session, 5 minutes after otherwise, doubling after each failure up to 30 minutes. A pull request saved before launch is asked about at launch, and one linked later at once, so its first report, whose alerts count as seen, comes before checks run on a new pull request. A merged or closed pull request is never asked about again; `pull-request-refresh` asks at once. A session with no pull request is asked about only while the surface shows it. When several sessions link one pull request, as a handoff or fork leaves them, only the newest is asked about in the background, and only it shows a dot or notifies; an older one shown in the surface is asked about while shown.
- `pull-request-dot`: a failed check run or a review or review comment the user has not looked at puts a dot on the session's row (`session-pull-request-dot-<id>`) and on the surface's tab (`surface-tabs-…-tab-N-dot`, `pull request-tab-0-dot` when the surface is alone in its strip, or `fitted-tab-<view>-dot` in a narrow window) for the selected session. The user has looked once an active window draws the surface for that session, and not while the settings page or the narrow window's sidebar covers it. A check that fails again on a rerun or a new head is new. What the first report for a pull request already holds counts as seen. Reviews and comments by whoever gh is signed in as (`gh api --hostname <host> user --jq .login`, asked once per host and again after gh reports a missing login), and the empty review GitHub adds for each thread reply, are not news. A merged or closed pull request has no dot. It never adds a Needs action reason: attention and the Needs action section are unchanged.
- `pull-request-notify`: the same new failures and reviews send a desktop notification ("Check failed", "New review") tagged `session-<id>-pull-request`, so on macOS it never replaces an approval's, as [notifications](notifications.md) does for a session no active window shows, except for a session whose pull request the active window shows, and unless Settings → Notifications → Pull request checks and reviews (`settings-notify-pull-requests`) is off.
- `pull-request-merge` shows on an open, non-draft pull request whose merge state GitHub reports as CLEAN, UNSTABLE or HAS_HOOKS, so never while the base branch's rules block it (BLOCKED), it is behind, has conflicts or GitHub is still working it out. It reads the methods the repository allows (`gh repo view <host>/<owner>/<repo> --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed`) and opens a confirmation (`merge-dialog`) with Squash and merge first when allowed, then Merge commit, then Rebase and merge; with more than one allowed they show as choices (`merge-method-squash`, `merge-method-merge`, `merge-method-rebase`). Confirm asks gh for the report again and sends nothing when it is no longer open or its merge state no longer allows it, saying why under "Could not merge.": "The base branch's rules block it.", "The branch is behind its base.", "The branch has conflicts.", "It is a draft.", "GitHub is still checking whether it can merge." or "It is no longer open.", since the merge endpoint does not hold back a user who may bypass the rules; otherwise it runs `gh api --hostname <host> --method PUT repos/<owner>/<repo>/pulls/<n>/merge -f merge_method=<method> -f sha=<head the user saw>`: GitHub merges at once or refuses, so nothing is queued or armed to merge later, and a branch that moved since is refused. Then the pull request is asked about again, and the button reads Merging… until gh answers. Cancel, Escape or a click outside sends nothing. A refusal shows gh's output under "Could not merge." (`pull-request-failed`, `pull-request-output`) until gh next answers.
- `pull-request-repair`: on an open or draft pull request, each failed check shows **Ask Claude to repair** (`pull-request-repair-N`), or **Ask Codex to repair** in a Codex session. It runs `gh run view --job <job> --log-failed --repo <host>/<owner>/<repo>` for the Actions job its details link names when that job is in the pull request's own repository, on a thread of its own, drops terminal colour codes, and puts `Fix the failing check \`<workflow / name>\` on <pull request link>.` and the log's first and last 32 KiB, fenced, in the session's composer, as tool output keeps them. A check with no Actions job in that repository, or whose log gh cannot read (as while other jobs of its run still run), gets its details link instead, and the latter shows "Log not read." with gh's words in the window's error line. A click while a log is being read does nothing. Each review comment shows **Send to Claude** or **Send to Codex** (`pull-request-send-N`), which puts `Address <author>'s review comment on <path>:<line> in <pull request link>:` and the comment, quoted, in the composer without asking gh. Text goes on lines of its own after the composer's cursor or selection, whose text it keeps; the composer takes focus and the draft is saved. A log that arrives after the window has moved to another session goes to a window that shows the session, else after its saved draft. Nothing is sent, pushed or merged: the user presses Send, and the usual steer rules apply during a running turn. The surface only shows the selected session's pull request, so there is no pull request without a session to pick one for.
- With no gh found, or gh exiting 4 for a missing login, the surface shows `gh auth login` (`pull-request-hint-gh-missing`, `pull-request-hint-gh-signed-out`, `pull-request-hint-command`, `pull-request-hint-copy`), as Changes does.

## How to get to it (user POV)

- Press Ctrl+Alt+P (Cmd+Alt+P on macOS), or choose **Toggle pull request** in the command palette. It opens beside the conversation, brings an open one forward, or closes it when focused.
- Click **+** on a tab strip and choose **Pull request**.
- Click the refresh button, a check, a comment, or **Merge**.
- Click **Ask … to repair** on a failed check or **Send to …** on a review comment, then Send in the composer.

## Driving it with keystone-verify

Preconditions: a disposable git repository as `KEYSTONE_PROJECT_DIR`, and the scripted Claude. `python3 scripts/fake-gh.py install <dir> <project>` makes `<dir>/bin/gh`; pass `PATH` with `<dir>/bin` first and a disposable `GH_CONFIG_DIR` in `start`'s `env`. It records each call as a JSON line in `<dir>/calls.log` and answers from the stage written to `<dir>/stage`: `running`, `failing`, `review`, `mergeable`, `blocked`, `merged`, `none` or `exit4` (see the script). Only the project's branch has a pull request. Merging moves the stage to `merged`.

`scripts/pull-request-journey.py` runs this journey end to end and checks each step. The journey: create a session in the project and a second one in a new worktree (Ctrl+Alt+G), select the first and open the surface; it finds #12 and shows the running check. Write `failing` and refresh: the failed check shows and no dot appears. Select the second session ("No pull request."), write `review`, and wait out the five-minute interval: the first session's row shows the dot, and `workspace` shows the same attention as before. Select the first: the dot clears and the comment shows `src/lib.rs:2`. Write `mergeable` and refresh, click **Merge**, then **Cancel**: `calls.log` has no `PUT`. Click **Merge** and confirm: the log ends with the `PUT` merge for squash and `sha=3f2c9e1`, the state reads Merged, and the log stops growing. Quit and relaunch: the surface shows the merged report again.

`scripts/repair-journey.py REPO OUT DRIVER` runs the repair journey at 1920×1080 with a live recording: the project has a bare remote; the `failing` stage's test check ran as job 9311, whose 76 KiB log has FIRST-LINE, MIDDLE-LINE and LAST-LINE. Ask Claude to repair: the session's saved draft names the check and holds both ends of the log and `bytes omitted`, not MIDDLE-LINE, and `calls.log` has one `run view --job 9311 --log-failed`. Send: the scripted Claude's `.fake-claude-messages` receipt is that text. Write `review`, refresh, Send to Claude on the comment: the draft is the quoted `src/lib.rs:2` comment, gh is not asked, and Send delivers it. A new Codex session on the branch shows Ask Codex to repair and Send to Codex. The bare remote's refs are unchanged and gh merged and pushed nothing.

## Not covered

- macOS: with `$VISUAL` and `$EDITOR` unset, a comment opens with `open`, through Files' editor helper.
- Keyboard choice of the merge method: Tab moves between Cancel and the confirm button only.

- Real GitHub. gh's JSON shapes come from its source (`api/export_pr.go`) and gh 2.102.0.
- Opening a comment at its line: the editor gets the file only.
