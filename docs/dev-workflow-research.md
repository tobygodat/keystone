# Development workflow research, 2026-10-16

The Grok CLI (`grok-4.7-build`) searched public web indexes for X posts after device-code sign-in. It returned post URLs and snippets. This was not an authenticated scrape of X or a full thread archive. Its initial claim that “X search is working” was too broad. The posts below are discovery leads; decisions use official documentation and local measurements. The CLI research session is `01a146d3-60d7-7331-b6c7-64131ef19a9c`.

## Findings that changed this round

- **Run integration test binaries concurrently.** Grok surfaced [RustRover's nextest post](https://x.com/rustrover/status/2040082404807725200) and [an agent-workflow discussion](https://x.com/tavisrudd/status/2043726632184422854). Nextest's [process-per-test design](https://nexte.st/docs/design/why-process-per-test/) explains the mechanism. Local five-run comparisons justified the explicit `core-fast` command with eight workers, no retries, and a separate Cargo doctest invocation. Public “up to” claims were not used as our speedup estimate.
- **Remove synthetic waiting before optimizing execution.** Local profiling found the old-Claude test sleeping after each of 200 words. Its replacement waits at the first streamed word until the test attempts the refused steer, then streams the remaining reply without pacing. This hypothesis came from our code and trace, not from an X post. All prior assertions remain.
- **Use the existing native automation.** Keystone already has the reusable headless driver and named controls needed for repeatable journeys. One unchanged typing-and-restart smoke passed with a 1,093-character draft, screenshots, saved state and successful cleanup. Installing another desktop automation stack would duplicate that capability. See the [workflow and commands](dev-iteration.md#native-verification-workflow).

## Next experiments, in order

1. **Completed the remaining long fake-Claude experiment.** Shorter replies and existing synchronization reduced the eight-worker check to 4.20 s. A subsequent 8/12/16-worker comparison selected sixteen and reached 3.26 s, with all 108 tests retained. The review rejected a restart gate that skipped the queued state under test. See the [second measurement pass](dev-iteration.md#second-measurement-pass). Keep the real shutdown deadlines; the next performance measurement should cover a content edit and rebuild.
2. **Use targeted tests during edits, then the full integration gate.** Nextest [filtersets](https://nexte.st/docs/filtersets/) can select a test or package. Check the selected list before running it. This changes coverage and must be labelled as a narrower edit-loop check, not compared as if it were the full suite. Run full `core-fast`, affected UI checks and required native/provider journeys before integration.
3. **Profile a real content edit before changing linkers.** Use [Cargo timings](https://doc.rust-lang.org/cargo/reference/timings.html) to identify the critical compile path. Hold compiler, flags, feature set, filesystem and cache policy fixed; time five alternating samples. An unchanged build or an mtime-only touch is not sufficient evidence of normal editing latency.
4. **Try Wild only if linking dominates that trace.** Grok surfaced [Rui Ueyama's mold release post](https://x.com/rui314/status/2107075031713128720). The independently read [mold 3.0 release notes](https://github.com/rui314/mold/releases/tag/v3.0.0) say its performance is on par with 2.42.1. [Wild's author's comparison](https://davidlattimore.github.io/posts/2026/09/18/benchmarking-wild-vs-mold.html) shows that filesystem, output-file reuse and forking can change the ranking. No linker change is justified by those posts alone. Keystone already uses mold and sccache.
5. **Measure GUI orchestration separately from application behavior.** Count driver startups, model/tool round trips, screenshots and total journey time. Reuse one desktop within a related journey; use named controls and condition waits. Group mechanical input only when focus and state are already known. Observe each meaningful transition and preserve screenshot/state evidence. Do not batch across uncertain state changes or shorten the typing-stress workload to manufacture a faster result.

## Ideas deferred

A shared Cargo target directory has already caused artifact interference in this project's parallel worktrees. Keep separate targets and share sccache. Grok suggested basedir/remap experiments, but this project's earlier audit already found those ineffective with its sccache 0.17 setup. Repeating them requires a new reason, such as a relevant upstream fix. Check cold builds and real edited-source rebuilds separately before disabling incremental compilation globally.

Nextest build archives and CI sharding may help a larger pipeline, but they add machinery to a local suite now around three seconds. Adding Tokio paused time would not accelerate this synchronous `std::thread::sleep` fixture. AT-SPI tools need actual accessibility support from the target app; browser or GTK examples do not establish GPUI support.
