# Devices

A session can have an iOS Simulator or an Android Emulator open beside it. The user sees it in the Device surface and taps it with the mouse; the session's agent drives the same device through the orchestrator's `device_*` tools. Keystone runs the user's own Xcode and Android SDK tools and installs nothing.

[ADR 0010](../adr/0010-terminal-browser-scheduling-editor-diffs-remote-devices.md) brought the device panel into scope and left two questions to this design. How frames reach the panel and input reaches the device is answered under Frames and Tools below. Whether a device can run on another machine is answered by the host seam: today only the local host exists, and a remote host is a second `DeviceHost` that TOB-306's remote environments design will carry.

## Host seam

`keystone_agent::device` is GPUI-free. `DeviceHost` is the whole interface: `inventory`, `start`, `wait`, `screenshot`, `act` and `shutdown`, each blocking until done or a `Deadline`. Callers run them on worker threads. A remote host (an SSH script runner or another Keystone process) implements the same six calls over its transport and reuses the pure parsers in `parse.rs`; nothing else crosses the seam. Points are fractions of the screen (`Point`, 0 to 1 on each axis), so neither callers nor hosts deal in points versus pixels.

`LocalHost` finds its programs through `KEYSTONE_XCRUN_PATH`, `KEYSTONE_ADB_PATH`, `KEYSTONE_EMULATOR_PATH` and `KEYSTONE_AXE_PATH`, then `PATH`, the usual install folders and the Android SDK's homes (`ANDROID_HOME`, `ANDROID_SDK_ROOT`, `~/Library/Android/sdk`, `~/Android/Sdk`). It looks again on each listing, so installing AXe or the SDK shows on the next Refresh. An override that names no file means the tool is missing; it never falls back to another copy. Every command runs in its own process group and is killed with what it started when its deadline passes.

| Platform | List | Start and wait | Screenshot | Input |
| --- | --- | --- | --- | --- |
| iOS | `xcrun simctl list devices available -j`, iOS runtimes only | `simctl boot`; then `simctl bootstatus` in 5-second steps, ending as not booted if the simulator shut down meanwhile | `simctl io <udid> screenshot --type=png <temp file>`, read and removed; `simctl io` can't write to a pipe. A shut-down simulator only makes it time out, so a failure on a simulator simctl lists as shut down or booting is `NotBooted` | AXe: `axe tap -x -y`, `axe swipe`, `axe type`, in points; `simctl launch` for apps |
| Android | `emulator -list-avds`, `adb devices -l`, `adb -s <serial> emu avd name` | detached `emulator -avd <name> -no-window -no-audio -no-boot-anim`, its output in a temp file of its own; then `sys.boot_completed`. An emulator that exits first fails the wait with its last line | `screencap -p`, guarded as below | `input tap/swipe/text` in pixels of the latest screenshot, which turn with the screen, else `wm size`; `monkey -p <package> -c android.intent.category.LAUNCHER 1`; each guarded as below |

Device ids are `ios:<udid>` and `android:<avd name>`, the same across boots. An emulator's serial (`emulator-5554`) stays inside `LocalHost`. Each lookup lists `adb devices -l` and asks each emulator's console its AVD with `emu avd name`, and keeps nothing of the answers: an adb server that restarts (`adb kill-server`) hands serials and transport ids out again from the start, so `emulator-5554` with transport id 1 can be another AVD than it was. Nothing that shows a frame, sends input or reads boot state trusts even a fresh lookup. Each runs as one `adb -s <serial> exec-out` script that prints `ro.boot.qemu.avd_name` and `ro.kernel.qemu.avd_name` and runs the command only when one of them is the AVD asked for. The serial is the one that AVD's last command ran at, else the one a lookup finds; when the emulator there names another AVD, nothing runs and the AVD is looked up afresh, and it is not running if the lookup's emulator names another AVD too. An image that sets neither property can't say so in the call, so its commands run at the serial a lookup found just before: `devices -l`, an `emu avd name` for each emulator adb lists, and the command, which is three calls per capture with one emulator against one for an image that names its AVD, and five with three emulators. Each of those commands still prints the properties, so an image that names its AVD later, as one early in its boot can, is back on one call from its next command. An emulator whose console names the AVD but whose image names something that is no AVD's, such as `sdk_gphone64_arm64`, can't be matched; a capture, an action, a start or a boot wait at it fails at once with "The emulator at <serial> calls itself <name>, which Keystone can't match to an AVD.", which the panel shows and `device_open` answers. `emu kill`, for Close and Quit, goes to the serial a lookup found just before, so an emulator that took a freed serial and port answers with its own AVD and is never shut down for another. `NotBooted` means adb lists no emulator running that AVD. An emulator adb lists but that can't say its AVD, such as one too loaded to answer in time, makes a screenshot, an action, a shutdown or a start of an AVD no other emulator runs fail with that error rather than call the device off or launch a second emulator beside it. While one can't say, a listing that would report an AVD off reports Android unavailable with that error instead. adb keeps listing an emulator that crashed as `offline` with its console port closed; an offline entry whose console refuses the connection counts as no emulator. One that is offline and fails otherwise, such as by timing out, can't say, and its error says that `adb kill-server` clears a stale entry. A boot wait keeps waiting through it, unless the emulator Keystone launched has exited, which fails the wait with its reason. A wait whose deadline passes while adb answers ends as booting, as on iOS. `LocalHost` keeps each emulator process it launched, so a shutdown before adb lists it stops that process group (SIGTERM, then SIGKILL in its last second) and answers once it has exited. Physical devices are not listed. iOS and Android list at once under the same deadline, so one platform stalling or failing never hides the other: each reports `Support::Unavailable` with the reason, such as a missing Xcode or SDK, and `Input::Unavailable` when AXe or adb is missing.

`start` returns at once with `Start::Booted`, `Booting` (by the user, another app or an earlier call) or `Started` (this call booted it). `wait` returns `BootState::Booted`, or `Booting` when the deadline came first and the boot carries on, or `NotBooted` when nothing runs or starts. Android text goes through the device's shell, so `input text` gets spaces as `%s` and shell characters escaped; text it can't carry (non-ASCII, a literal `%s`) is refused, never altered. App ids are checked to be names before they reach a shell.

AXe taps in points. After a screenshot, `LocalHost` learns the simulator's point size from `axe describe-ui` on a thread of its own, so a tap is one AXe call. It learns again when the screen turns between portrait and landscape, and forgets the size on shutdown. Only one learn runs at a time per simulator: a tap while one runs waits for it, since two AXe sessions at once are what make a loaded simulator time out. A tap before the size is known learns it first. A failed learn waits 10 seconds, then 20, before a screenshot tries again, and screenshots stop trying after three failures; taps still ask. A size whose shape doesn't match the screenshot it was learned for is marked unreliable, and each tap asks AXe afresh instead. When AXe says it timed out creating the simulator's automation session, which a loaded machine causes, the call runs once more if the deadline leaves as much time again.

## Tools

The `keystone` MCP server publishes eight tools beside the session and `browser_*` tools, listed in `mcp::device::TOOLS` with their schemas in `mcp/device.rs`, as the browser's are in `mcp/browser.rs`. Their descriptions say "beside this session".

| Tool | Behavior |
| --- | --- |
| `device_list {}` | `{host: "local", devices: [{id, name, platform, os, state}], platforms: [{platform, available, reason?, input, input_reason?}], open}`. `state` is the host's own: `shutdown`, `booting` or `booted`. |
| `device_open {device}` | Opens the device beside the caller at once, replacing the device open there, and boots it if needed. An open of a device already starting joins that boot. An id the latest listing doesn't name is listed again first; if it is still missing, the answer names the devices there are and nothing beside the session changes. No device id or app id may start with `-`, so none reaches `adb`, `emulator`, `simctl` or AXe as an option. Answers `{device, state: "booted"}` once it has booted, or `{device, state: "booting"}` a second before its 50-second budget runs out, `"shutting_down"` when Keystone was still shutting it down then; a later call waits again. |
| `device_screenshot {}` | `{device, width, height}` plus the screen as MCP image content. |
| `device_launch {app}` | A bundle id (iOS) or package name (Android). |
| `device_tap {x, y}`, `device_swipe {x, y, to_x, to_y}` | Pixels of the latest `device_screenshot` image this session got. A tap before any screenshot is refused: "Take a device_screenshot first". |
| `device_type {text}` | 1 to 1024 characters into the focused field. |
| `device_close {}` | Removes the device from beside the session. `{device, shut_down}`: Keystone shuts it down only when Keystone booted it and no other session holds it, and then answers once it has. A close that has to wait for the device's start or shutdown longer than its budget answers `{device, state: "closing"}`, or `"shutting_down"` while Keystone's shutdown, which may still fail, is running, and goes through when that ends. A failed shutdown is an error, and the device stays open beside the session. |

Every call needs a caller with a running turn, as the session tools do. `device_list` and `device_screenshot` work for every such caller, including read-only sessions and second opinions; a second opinion's screenshot shows the device open beside the session it reviews. The other six are refused for read-only callers and for second opinions and their handoffs and forks. Claude auto-allows the device tools (`mcp::auto_allowed`, beside the session tools and the browser tools that stay on this machine), so Ask mode does not prompt for device control: the simulator is a sandbox the user watches. A stricter policy for Ask is an open product question.

**Budgets.** `protocol::budget` gives `device_open` 50 seconds and the other `device_*` tools 20 (`mcp::device::budget`), the `browser_*` tools 40, and every other tool 5 (Codex allows 60 per tool call). The host call ends one second before the tool's deadline, so the answer still goes out in time.

**Images.** A handler returns `mcp::Reply { value, images }`, the one path for images: `browser_screenshot` returns its JPEG the same way. The server sends `content: [text(value), {type: "image", mimeType, data}]` and `structuredContent: value`, never the bytes. The model's copy is scaled to fit a 1568 px long edge and 1.15 megapixels (a 1206×2622 iPhone frame becomes 721×1568), sent as PNG, or JPEG at quality 85 when the PNG is over 1 MiB.

## Desktop

`device/mod.rs` holds `Devices`, the app-level state. Each session holds at most one device (`Beside`), with the number of the open that put it there. Each device Keystone deals with has one `Record`: its `Lifecycle`, the opens and closes waiting on it, and a `Screen` entity with the latest frame and error. `device/life.rs` is the `Lifecycle`: the device's `Life`, whether Keystone booted it, the start Keystone waits on and a shutdown that failed, with one method per answer from the host and no GPUI, so each transition is tested alone. Nothing of it is saved: after a restart a simulator may be off, and restoring "open" would claim what nobody observed. `device/tools.rs` authorizes and parses the tools and builds their JSON, `device/capture.rs` paces captures, `device/frames.rs` decodes frames and `device/pane.rs` draws the surface, a layout component like Pull request.

A request runs in three steps. The UI thread authorizes it (`caller`, `reviews`, the approval mode). One `Worker` per device runs its short host calls (start, screenshots, input, shutdown) in order, so a slow device blocks neither the UI nor another device; listing has its own worker, and the wait for a boot runs on a thread of its own so it never holds up the lane. Each host call returns a `Done` that carries what it was asked, and the UI thread applies it, then answers the caller after checking it again. A job that panics answers as a failed call ("Keystone's call to the device failed unexpectedly"), which the lifecycle takes like any other failure, so a start that panics leaves the device Failed and the next open asks again; its lane runs on. The user's Open, Close and clicks on the frame take the same path without an answer.

**Lifecycle.** An open makes the session hold the device at once and asks the host to start it. The device is Starting until the host answers, then Booted, or Booting while Keystone waits up to three minutes for the boot, then Booted, Not running, Failed or Still booting (Keystone stopped waiting; the boot may finish later). Opening a device that is running keeps it Running, its frames and input going, while the host confirms it; only a start answer that disagrees, such as one that had to boot it, changes it, and an answer to an older start is ignored. Opening a device that is starting, booting or shutting down joins it. An agent's open is answered when the device boots or fails, or as booting before its deadline. An open the session has since replaced answers that the device is no longer open there, and never moves the session back.

After every change, `settle` decides what becomes of the device, on the UI thread, with what is true then. A close lets go at once while another session holds the device. Once no session holds a device Keystone booted, Keystone shuts it down, and the close waits for that; nothing shuts down while a start is still to answer. A device that turns off stops being Keystone's, so one the user boots again outside Keystone keeps running after Close. A device nobody holds and Keystone need not shut down is forgotten. Replacing a device beside a session lets go of the old one the same way. A failed shutdown keeps the life the device had (a boot still being waited on stays Booting, never Running), keeps it open beside the closing sessions, answers the opens that joined it, and says why in a note on the Device panel of each session that still has it open (`device-refused`), which neither frames coming in nor a listing clear while a session still has it open, until an open or a close tries again; Close tries again. A device no session holds whose shutdown failed stays Keystone's, its picker row says why, and the next listing (Refresh), an open or Quit tries again.

Quit shuts down every device Keystone booted, at most three seconds in all, calling the host directly so a start or capture still running on the device's lane can't hold it up; a shutdown Keystone already runs is left to finish, never started twice. A device whose start is still running is shut down once that start ends, if the start booted it, so Quit right after Open leaves nothing booting; a device the user had running stays running. Jobs still queued return without calling the host. Then Quit calls the host's `stop`, which kills the process group of every command still running, such as a capture hung on a lane, and refuses new ones; `LocalHost` keeps each command it runs in a `git::Children` set for that, because a command's own deadline lives on a thread that dies with the app.

Asking for a listing while one runs lists once more after it, however many asked. A listing that fails says so in the picker and to the agent. A listing that finds a device running brings it back from Not running, Failed or Still booting.

**Frames.** `Keystone::note_device` reports each frame which session's Device surface the window drew, unless the settings page or the narrow sidebar covers it. A shown, running device is captured again 250 ms after the previous capture ends while an active window shows it, 2 seconds while only inactive ones do, and not at all otherwise. One capture runs per device at a time, on its lane, and a tool's screenshot or action updates the panel too; an action captures at once. Decoding and the 1200 px thumbnail happen on the lane; the previous image is dropped from every window's atlas (`cx.drop_image`). A frame updates only the device's `Screen`. Each window's Device surface is a cached view that observes the app state and the `Screen` of the device it shows, so a new frame redraws only the windows showing that device and never notifies the app state (ADR 0007). Frames come only from real captures; one older than five seconds, after a failed capture or while the device isn't running is labelled with its age. While a frame shows, a timer on the panel redraws that panel alone when the frame turns five seconds old, and each second while its age label shows, so the label counts up while a capture is stuck or after one failed. The panel follows the `Screen` entity itself, so a device closed and opened again while the surface was hidden draws its new frames.

**Surface.** Device is a side surface (`Component::is_side`), like Files and the Browser: it opens beside the composer's column where the window is wide enough, beside the conversation under the composer where it isn't, and as one of the window's fitted tabs at narrow widths. It takes the side panels' 220 px minimum; a phone frame fits itself to whatever the pane gives it, so it needs no more. It opens with Ctrl+Alt+V (Cmd+Opt+V on macOS; Cmd+Opt+D would hide the Dock), the `toggle-device` command, which Settings → Shortcuts can rebind and which works from a terminal pane too, since the terminal hands only plain Ctrl+letter keys to the shell (`terminal::shell_keys`), **Toggle device** in the palette, or **Device** in a tab strip's + menu. With nothing open beside the session it lists devices (`device-row-N`, `device-open-N`), each with what Keystone holds for a device it opened, else what the latest listing found, each platform's reason when it can't run here, and on the row of a device no session holds why Keystone couldn't shut it down (`device-refused-N`). With a device open it shows the name, OS and phase (`device-name`, `device-phase`: Opening…, Booting…, Running, Still booting, Not running, Shutting down… or Failed), notes such as why it failed, in the panel's own words, the frame (`device-frame`) fitted to the pane, Refresh (`device-refresh`) and Close (`device-close`). A click on the frame taps there and a drag swipes, to the screen's edge when it is let go past the frame, unless the platform has no input tool, when a note says how to get one. The first time an agent opens a device beside a session, each window showing that session opens its Device surface without moving focus; a window opened later doesn't act on that.

## Limits

- Local host only. `HostId::Local` is the only host, and `device_list` says so, so a later `host` argument is additive.
- Beside a session on another machine the panel says devices aren't available for sessions on that machine yet, and lists, captures and runs nothing here; each `device_*` tool refuses such a caller by machine name (`AppState::device_elsewhere`). See [remote machines](remote.md#devices-on-other-machines-tob-307).
- No device streaming: frames are screenshots, about 1.3 per second on iOS at roughly 0.5 s per `simctl io`.
- No hardware buttons, rotation control, app install or physical devices.
- iOS input needs AXe (`brew install cameroncooke/axe/axe`).
- The panel's controls are pointer-only apart from the toggle shortcut.
