# Provider integration design

Status: Codex and Claude Code are implemented as described, in `crates/keystone-agent` (2026-10-15). The spike results below have been folded in. Log IO, history loading, and provider startup run off the UI thread, and the transcript is virtualized (2026-10-16; see sections 3 and 10). [Claude Code in practice](#claude-code-in-practice) records what the Claude driver does that the spike did not show, and what is not built yet.

Keystone drives the user's own installed `claude` and `codex` programs. This document says how, and where it deliberately differs from Zeron (MIT, Rust, studied at commit `3b2f780`) and T3 Code. Protocol facts were checked against Claude Code 2.1.300 and codex-cli 0.162.1 on 2026-10-15.

## What Keystone needs

From [the product scope](../adr/0001-product-scope.md): local execution, provider-native capabilities and configuration, steering-only messages during active work, native compaction, approvals that settlement never grants, detailed agent activity, checkpoints and rollback, cross-provider handoff and second opinions, recovery of interrupted work, and import of existing provider sessions. From the working preferences: low build time, measured performance, and native verification.

Keystone is one local process with one window owner. It does not need multi-device sync, a mobile client, or an RPC layer between its own parts.

[Local orchestration](orchestrator.md) adds a loopback MCP tool surface for active
Keystone sessions to launch, steer, read, wait for and interrupt other sessions,
without replacing either provider's native tools or system prompt.
Launch permission is checked at admission under the connection lock. The child's
initial write rechecks the parent's live generation and current approval ceiling,
but does not require its admitting turn to remain running during initialization.

## Design

### 1. Drivers are pure state machines

A driver turns provider output into Keystone events and Keystone commands into provider input. It never spawns, reads, writes, sleeps, or sets timers.

```rust
trait Driver {
    /// Feed one complete output line. Returns events and any lines to write back.
    fn on_line(&mut self, line: &[u8], out: &mut Outputs);
    /// Translate a user action into provider input lines.
    fn command(&mut self, command: Command, out: &mut Outputs);
    /// The process ended. Close any open turn with a terminal status.
    fn on_exit(&mut self, status: ExitStatus, out: &mut Outputs);
}
```

One `ProcessHost` owns every child process: spawning, line framing, stdin writes, stderr draining into a bounded tail, and process-tree teardown. Drivers are tested by replaying recorded transcripts, so the edit loop never starts a provider. This is the "scripted providers exercise the same protocol boundary" rule in [the conventions](../CONVENTIONS.md#tests).

Zeron's drivers combine all of these concerns with fallback timers. Most of its documented bugs (doubled input requests, stale completions, mis-tagged task notifications) sit where IO and protocol state meet.

### 2. Items, not delta events

The model is a list of items per turn, each with a stable ID: `UserMessage`, `AgentMessage`, `Reasoning`, `ToolCall { kind, input, output, status }`, `Approval { request, decision }`, `Plan`, `Compaction`, and `Notice`. Both providers already speak in items: Codex has `item/started`, deltas, and `item/completed`; Claude has content blocks with partial-message stream events.

A delta appends to the live item's text in place. It does not become a message on a channel, a journal line, or a copy. The reader thread updates the session's live turn under a short lock and sets a dirty flag. The UI thread checks the flag once per frame and re-renders only the live item. That limits UI work to the frame rate however fast tokens arrive. It also attacks the cause suspected in KS-005: a backlog of synchronous redraws.

Completed items never change, so their layout can be cached. The transcript uses GPUI's virtualized `list` with bottom alignment, so a long session costs only its visible rows. The list has one entry per row plus a status entry (approval card, "Working…", errors) after the last row. The conversation reports which rows it added or changed, and only those are remeasured; the status entry is remeasured on every change. The list follows new rows while it is scrolled to the bottom. Once the user scrolls up, it keeps the row at the top of the view at the same offset, even while that row streams or a row above it changes. Sending a message or selecting a session returns to the bottom. Row content comes from one function, `transcript::row`, so a change to how rows look, such as Markdown, stays out of the list code.

### 3. Storage: the provider owns the conversation; Keystone keeps a neutral log

**Decide.** One workspace SQLite database holds neutral completed items, approval decisions and turn boundaries alongside sessions and preferences. A global append-only event sequence accompanies the read projections. Nothing is written per streamed delta. The log worker commits completed batches atomically with WAL and synchronous=FULL; workspace changes use guarded transactions. Existing `workspace.json` and `sessions/*.jsonl` are imported once, together, and left untouched. See [storage](storage.md) for transaction, retry and migration guarantees. Tool output is kept with a cap: the first and last 32 KB plus the byte count.

Why keep a log when the providers keep transcripts:
- Claude's transcript format is "internal … and changes between versions" according to its own docs, so Keystone cannot depend on it at runtime.
- Handoffs and second opinions need one neutral representation across providers.
- Showing history should not require starting a provider process.

Provider transcripts are still the source of truth for the conversation itself. Resume uses the provider's session ID (`--resume` for Claude, `thread/resume` for Codex), never a replay of Keystone's log.

**Order.** Each item, decision, and shown turn end carries `seq`, its place in the transcript as it was shown: the order in which its row first appeared. A restore sorts rows by it. Completion order is wrong for steering: a steer is shown, and logged, while the reply it interrupts is still streaming, and that reply is logged only when it completes. Logs written before `seq` existed have none; their rows keep file order, and rows written later are placed after them. Each placed entry also carries `run`, which identifies the run of Keystone that wrote it, and its `seq` counts from the first row that run added. A restore places each run after every row before it. So a run never needs the saved history to log in the right place: when the history cannot be read, or has not arrived when Keystone closes, what happens is still saved and later restores after the history.

**Off the UI thread.** The desktop's conversation state does no IO. It collects entries in an outbox, and `log::Logs` writes them on one worker thread for all sessions, in the order they were queued, so a session's entries stay in order. Each history load reads on a thread of its own, so a read that never returns, such as from a FIFO or a stalled network disk, holds up neither writes nor other sessions' loads. A session's history is requested once, the first time it is needed, before anything is written for it, and arrives as a report; events and sent messages that arrive meanwhile wait and are applied after the history. If the read fails, the conversation goes on without the history and shows a warning for the rest of the session; what was sent meanwhile is shown and saved. A message sent meanwhile has already gone to the provider, so the turn shows as running, with Stop, at once. A write failure is reported to the conversation and shown until a later write succeeds; the next write reopens the file. Quitting and closing the window first wait up to two seconds for history still loading and apply it, so messages waiting on it are logged. A history that has not arrived by then is given up, which logs what was waiting on it; the read is left running and is not joined. Then they wait for every queued write, without a bound, so a disk that stalls writes still holds up quitting. `worker::Worker` is the general piece and does not know about Codex.

On startup, a session whose log has no turn end is marked interrupted, and Keystone checks what the provider saved; see [crash recovery](#crash-recovery). SQLite does not itself recover unfinished provider output.

Import of existing sessions reuses the same readers. It is a versioned, best-effort, one-time conversion into a Keystone log, never a live dependency.

SQLite is synchronous and bundled through rusqlite, without an async runtime. Its global sequence leaves a cursor for a future client, but remote sync, delivery orchestration and a CRDT are not part of storage.

### 4. Turns end only when the provider says so

The core runs one lifecycle per session: idle → running → (awaiting approval ↔ running) → ended with `completed`, `interrupted`, or `failed`.
- **Claude:** the turn ends at a `result` once every message sent during it has finished, as reported by `command_lifecycle` frames. A steer can produce one `result` or two, so counting results is not enough. Output that arrives while idle starts a turn the agent began itself, such as after a background task.
- **Codex:** the turn ends at `turn/completed`.
- **Process exit:** `on_exit` closes any open turn as failed with the stderr tail.

The driver also reports whether the user ended the turn: with Stop, or with a denial the provider ends the turn on. Codex's `decline` lets the turn go on and its `cancel` ends it; the driver sends `decline` when Codex offers it. Only the driver knows which turn an interrupt or a `cancel` reached, so it carries this on that turn's end (`stopped`), and the desktop counts an interrupted turn as a failure unless it was stopped. A Stop that drops messages Codex has not received yet ends that turn in the driver; a Stop that arrives after the turn ended does nothing, so it never replaces that turn's end. Claude's deny always lets the turn go on, so only Stop marks a Claude turn stopped: the driver sends `interrupt` only while a turn runs, and that turn's end carries `stopped`. Stop on a message still held for a mode confirmation ends that turn in the driver as stopped, as it does for Codex. A mode that Claude refuses or does not confirm in time fails the turn instead. A crash or an explicit failure stays a failure.

There are no watchdogs, heartbeats, or quiet-period timers. Zeron added and later retired several of these after "stuck working" incidents. Capabilities are data detected at startup (Claude's `system/init` capabilities, Codex's `initialize` response), not trait booleans.

### 5. Process topology

**Decide.**
- **Codex:** one shared `codex app-server` for the whole app. Threads are multiplexed by ID, model listing uses the same process, and probe processes go away. If it crashes, a supervisor restarts it and resumes the threads that were loaded. The spike confirmed two threads running turns at the same time in one process. Memory decides it: an idle app-server with one thread used about 650 MB across 4 processes, and each extra thread added about 150 MB (three helper processes from the user's Codex configuration). Six sessions measured 1.4 GB shared, against about 3.9 GB estimated for six separate processes. Startup is not a reason; a cold app-server answered `initialize` in 0.09 s. Keystone unsubscribes threads that have been idle, so Codex unloads them and their helpers.
- **Claude:** one process per active session, as the protocol requires. An idle process measured 256 MB and answered `initialize` in 0.29 s. A process proven idle for 10 minutes may be stopped and resumed lazily, but that is off for every real Claude profile; see [Idle shutdown](#idle-shutdown). When the user starts typing in a new Claude session, Keystone may start the process early to hide startup; measure before keeping that.

Children start in their own process group. Teardown sends the protocol interrupt, then SIGINT, SIGTERM, and SIGKILL with short grace periods, then kills descendants found through `/proc`. Agents put shells in separate groups, so the group alone is not enough. Zeron learned this; Keystone avoids spawning `ps` to do it.

### 6. Permissions are real

- **Claude:** Keystone passes `--permission-prompts host --permission-prompt-tool stdio`. The spike showed that `--permission-prompts host` alone does not reach Keystone: Claude denied the tool itself and emitted `system/permission_denied`. The `stdio` value is undocumented, but the official Python SDK passes it whenever a permission callback is set (`types.py:2288-2304`), so Anthropic's own SDKs depend on it. Each `can_use_tool` control request becomes an `Approval` item.
- **Codex:** Keystone sends the user's own approval policy and sandbox settings. It does not force `never` and full access. Its approval requests also become `Approval` items.
- **Inbox:** an approval blocks its turn and appears in the attention inbox. Settlement never answers it, which the scope requires.
- **Approval modes:** each session has a mode the user can change at any time, mapped to the provider's own settings. Claude takes `--permission-mode` at launch (`manual`, `acceptEdits`, `auto`, `dontAsk`, `plan`, `bypassPermissions` on 2.1.300) and the `set_permission_mode` control request mid-session. Codex takes `approvalPolicy` (`untrusted`, `on-request`, `never`) and a sandbox on every `turn/start`, so a change applies from the next turn. Keystone shows an approval only when the chosen mode asks for one. The default is whatever the user's own Claude and Codex configuration says.

  Built 2026-10-15 and reworked 2026-10-16. The modes live in `keystone_core::ApprovalMode`, are saved per session, and are chosen from the composer's shield button.

  **The rule.** A user message, whether a new turn, a steer, or a retried turn, is written to a provider only after checking, at that moment and under the lock every mode change takes, that the provider is in the session's latest mode. Otherwise the message waits while Keystone brings the provider to that mode, and it fails visibly if that cannot be done; it never goes out under another mode. For Codex the mode is part of each `turn/start`, so a steer into a turn started under another mode waits and starts the next turn instead. For Claude the check is `ClaudeDriver::mode_confirmed`, described below.

  | Mode | Codex `approvalPolicy` / sandbox | Claude `--permission-mode` |
  | --- | --- | --- |
  | Provider settings (default) | nothing sent | none passed |
  | Read only | `on-request` / `readOnly` | `plan` |
  | Ask first | `untrusted` / `workspaceWrite` | `default` (2.1.300 also calls it `manual`) |
  | Auto | `on-request` / `workspaceWrite` | `acceptEdits` |
  | Full access | `never` / `dangerFullAccess` | `bypassPermissions` |

  **Path to the provider.** The mode goes through the `Connection` trait, which is provider-agnostic. `send` carries the session's `ApprovalState` (the mode and whether an override may exist), and `set_approval` changes it at once. Each connection keeps every session's state in its shared state, under the lock its drivers run under, and gives it to the driver (`Command::Configure`) before the driver handles the session's messages. So a replacement process after an exit gets it too, and a turn the driver starts later on its own, such as a Codex steer that becomes the next turn, uses the latest mode. The composer's menu saves the mode and then calls `set_approval` on the session's connection, if it has started.

  **Saved before it is sent.** `Store::set_approval_mode` saves the mode and, for any mode but the default, `approval_overridden` in one write. Nothing reaches a connection unless that write succeeded, so no provider can hold an override Keystone has not recorded. A session saved by an earlier build with a mode but no record gets the record saved before its next message; if that fails, the message is not sent and stays in the composer. The record is never cleared. A write whose directory sync is pending counts as saved: the file is in place, and only a power loss before the sync could lose it.

  **Codex keeps overrides.** Codex keeps a `turn/start` override on the thread, including across `thread/resume`; a probe against codex-cli 0.162.1 confirmed it. Returning to Provider settings therefore sends the user's own settings, and once a thread may hold an override, every Provider settings turn sends them, not just the first. A restoring turn Codex rejects, or one lost with its process, cannot leave the old override for the next turn to inherit, and nothing needs tracking whether a restore landed. The driver takes the settings from the `thread/start` response, which reports the effective settings for the directory. A resumed thread reports its old override instead, so when `approval_overridden` is set, the driver opens one ephemeral `thread/start` in the same directory to read them, and the next turn waits for that answer. If the settings cannot be read, the message fails with an error; it never runs under the override the user turned off. The mapping is `keystone_agent::codex::policy`.

  **What Claude keeps.** Probes against Claude Code 2.1.300 on 2026-10-16 showed that a `--resume` without `--permission-mode` does not reliably start in the user's own setting. A process launched in `bypassPermissions`, or changed to `acceptEdits` in place, resumed in the project's `defaultMode` (or `default`), but one in `plan` resumed in `plan`. With `--permission-mode` given, the resumed process starts in that mode. So Keystone passes the mode on every launch and every resume when it selected one. With Provider settings, a new conversation gets no flag. A resumed one whose `approval_overridden` is set gets the user's own mode, read first from a fresh `claude` that is closed after it answers `initialize` (its `current_permission_mode`). If that fails, the message fails and asks the user to choose a mode.

  **Claude's confirmed mode.** Nothing is written to a Claude process before it answers `initialize`, which reports its `current_permission_mode`. After that the driver tracks the mode Claude last confirmed: answers to `set_permission_mode` and its `system/status` and `system/init` reports. Every message waits in the turn's held list, and the driver writes it only when Claude answered `initialize`, no `set_permission_mode` is unanswered, the confirmed mode is the one the latest selection needs, and the process is not one that must be replaced. With Provider settings, the last condition means Keystone never changed this process's mode. Otherwise, when nothing else is pending, the driver asks Claude for the mode. Each request records the version of the selection it was sent for, and the version goes up with every change. An answer always updates the confirmed mode, but held messages go out only once it is the latest selection's mode and no other request is pending, so an answer for an older selection triggers a new request instead. A refusal of the latest selection fails the waiting turn with nothing sent. Stop leaves no gate behind: a request still unanswered only means the mode is unknown until Claude answers it. A request unanswered for 20 seconds fails the messages waiting for it, and the process is replaced before anything else is written to it.

  **Usage at start.** Once a chat process answers `initialize`, Keystone writes `{"subtype":"get_usage","skip_behaviors":true}` as request `keystone-usage`, outside the `keystone-N` numbering, after any `mcp_set_servers` and before any message. Nothing waits for it and it is never timed. A `success` answer with `rate_limits_available: true` reports each window of `rate_limits` that Keystone has a label for (`utilization` a percentage, `resets_at` RFC 3339) as `Event::Usage`, like a `rate_limit_event`. Claude Code 2.1.301's `model_scoped` is left out rather than shown under its raw ID. A window a `rate_limit_event` already reported in the process is left out too, since the answer was asked for earlier. The schema is experimental, so an error, `rate_limits_available: false`, or any shape Keystone cannot read reports nothing and changes nothing else. The layout helper does not ask.

  **`ExitPlanMode`.** Approving Claude's `ExitPlanMode` returns it to the mode it had before plan mode, not to `default`. Live, a process launched in `acceptEdits` and set to `plan` reported `acceptEdits` after the approval, and wrote a file without asking. So under Read only Keystone refuses `ExitPlanMode` itself, tells Claude to present the plan and stop, and shows a warning; the user is not asked. Under other modes the user decides as usual. Claude leaves plan mode when the tool runs, which no later line Keystone writes is ordered against, so after an approval nothing more is written in that turn: steers sent meanwhile start the next turn, which confirms the mode first.

  **Changes that need a new process.** Claude refuses `set_permission_mode` to `bypassPermissions` unless the process was launched in it (`bypass_not_launched`). A process launched in it is never lowered in place. The user's own settings come back only in a process whose mode Keystone never changed. So entering or leaving Full access, returning to Provider settings after Keystone set a mode, and a process whose mode request timed out need a new process, resuming the conversation. The session's worker replaces a process only when nothing of the turn was written to it: before an idle process's next turn, or when a turn's messages are still all held, such as when the mode changed while the process started. The held messages move to the new process as the same turn. Steers held during a turn that needs a new process start the next turn when the running one completes. While a message waits to start in a new process, a second one is refused like any steer before Claude reports lifecycle support, and the text stays in the composer.

  Full access shows in the warning color. Choosing it from the menu opens a confirmation dialog first, which names the session's provider and says it will run commands and edit files without asking. Until Confirm nothing changes: the mode is not saved, `set_approval` is not called, and no Claude process is replaced, so work already sent, such as a steer Codex turns into the next turn, still runs under the previous mode. Cancel, Escape, or a press outside the dialog leaves the previous mode. Confirm takes the same path as every other mode: one write of the mode and `approval_overridden`, then `set_approval`. The dialog is modal, and the app's shortcuts are off while it is open, so Ctrl+Enter cannot send. Leaving Full access, choosing the current mode again, and restoring a saved Full access session at startup ask nothing.
- **Questions:** built 2026-11-02 (TOB-296), from frames recorded with Claude Code 2.1.316 and codex-cli 0.166.0 ([probe](../research/questions-probe.md)). Claude's `AskUserQuestion` (a `can_use_tool` request), Codex's `item/tool/requestUserInput`, and an MCP server's form (Claude's `elicitation` control request, Codex's `mcpServer/elicitation/request`) each become one `keystone_agent::Question`: fields that are a single or multiple choice, with typed text when the asker allows it, free text, or a number. `Command::Reply` carries one `Answer` per field, or `None` to decline, and the driver writes it in the provider's own format: Claude's `allow` with `updatedInput.answers` keyed by question text (several choices joined with ", "), Codex's `{answers: {id: {answers: [..]}}}`, an MCP form's `{action: accept, content}` with each property in its schema's type. A form's `minimum`/`maximum`, `minLength`/`maxLength` and `minItems`/`maxItems` hold the answers given before Submit turns on; `pattern` and `format` are not checked. A required list without `minItems` may be left empty and is sent as `[]`; a required text field must be filled. Declining sends Claude a `deny`, Codex empty answers, and an MCP server `decline`; in the recordings each provider then went on with its turn. A form with no fields only asks to go ahead, as Codex does before an MCP tool call (`codex_approval_kind: mcp_tool_call`), so it is an ordinary approval whose Allow accepts it empty. URL-mode elicitations, forms with fields Keystone cannot show (nested objects) and Codex questions marked `isSecret` are declined at once, with a warning in the transcript. A question resolves like an approval: `control_cancel_request`, `serverRequest/resolved` or the turn's end withdraw it, and a later answer is not sent. Codex offers `request_user_input` in Default mode only when the user's config sets `features.default_mode_request_user_input`; otherwise only in Plan mode, which Keystone does not use (ADR 0001).

  The desktop shows the first waiting question as a card under the transcript, after any approval, and the session's attention reads "Waiting for your answer", as for a widget. Settlement never answers it. Answers in progress are kept in the app's `Conversation`, so closing every window loses none. Questions are never saved: a process that asked one ends at quit, so after a relaunch nothing waits for it and the turn reads as cut off, as with a pending approval.
- **Unknown requests:** any control request or server request Keystone does not handle gets an explicit error response, so the agent never waits forever. Zeron leaves unknown Claude control requests unanswered.

### 7. Parsing

Each line gets a cheap first pass that reads only its method and ID, skipping the body, then one typed decode of the parts Keystone uses. Fields Keystone does not show are skipped without being built. Large tool output is read through a capped field, so it is never fully allocated. Unknown message types are counted and, in debug builds, logged raw; they are never fatal.

Codex's `optOutNotificationMethods` turns off notifications Keystone does not render, so they are never sent at all. The spike saw `remoteControl/status/changed`, `account/updated`, and per-thread `mcpServer/startupStatus/updated` alongside the turn traffic.

The message types are written by hand for the subset Keystone uses. A test validates them against the JSON schema generated by the pinned Codex version.

### 8. Steering and interrupt

Steering follows the scope: a message sent during a turn steers that turn, and there is no follow-up queue.
- **Claude:** a user message with priority `now`, or `next` while a tool is running, because `now` aborts a running MCP call. Zeron found this rule; credit it. In the spike, a `now` steer ended the current response with a `result` (`terminal_reason: aborted_streaming`), then a second `result` followed with the steered reply. A `next` steer sent during a tool call was folded into the running turn in one recording, with a single `result`, and ran as its own turn in another. Keystone shows all of these as one user-visible turn.
- **Codex:** `turn/steer` with the expected turn ID. In the spike, the same turn continued and completed with the steered reply. If the turn already ended, the message starts the next turn.

Interrupt uses Claude's `interrupt` with `cancel_queued` when the `interrupt_cancel_queued_v1` capability is present, or Codex's `turn/interrupt`. In the spike, Claude ended with `result` subtype `error_during_execution` and stayed running; Codex ended with `turn/completed` status `interrupted`. Interrupting a turn does not stop background tasks. Stopping the runtime does, and asks first when background work is live.

### 9. Version safety

A table lists the tested version range for each provider. Keystone reads `--version` once per binary and caches it on disk by path, size, and modification time. An untested version shows a warning in the UI and still runs. Recorded transcripts from each tested version live in `crates/keystone-agent/tests/fixtures/`. An opt-in `bash scripts/check.sh live` runs one tiny real turn per provider in a disposable repository and checks that the driver sees every message type it expects. It uses the user's subscription, so it never runs by default.

### 10. Crates and threads

A new `keystone-agent` crate holds items, drivers, the session lifecycle, the process host, and the log store. It does not depend on GPUI, so its tests compile without the graphics stack. The desktop crate only renders and sends commands.

The process host uses one blocking reader thread per child process for stdout and one for stderr, plus a writer thread with a bounded queue. That is a few threads per active session and no async runtime in Keystone's own code. `async-process` and `smol` are already compiled through GPUI if that changes.

The UI thread never blocks on a provider or the disk. Provider commands go through a `worker::Worker`, in order, so finding the program and spawning it happen there, outside the connection's lock: a start that stalls, such as on a hung disk, holds up only the commands waiting on that process. A start failure arrives as a `Failed` event for the session that needed it. The connection keeps its event inbox under its own lock, so draining events never waits for a process to start. Codex has one worker for its one app-server. Claude has a worker per session, so one session stuck starting never delays another's messages, Stop, or answers, and its events go through the same conversation, `log::Logs`, and transcript as Codex's. A starting Claude session's driver takes its first message before the spawn and keeps what it writes and reports until the process is in place, so output Claude prints before reading anything, such as a failed `--resume`, still belongs to that turn. Dropping a connection does not wait for queued commands. It waits up to two seconds for a start in progress, so the process it starts is ended; a start stuck longer is given up on and ends its own process if it ever starts while Keystone still runs. The one error `send` returns at once is a steer the provider cannot take now (see [Claude Code in practice](#claude-code-in-practice)); the text then stays in the composer.

### 11. Model choice

Built 2026-10-17. Effort, speed, and changes after the first Send built 2026-11-02 (TOB-297) from [the model settings probe](../research/model-settings-probe.md), which has the evidence for every protocol rule here.

**What is chosen.** A session asks its provider for a model, an effort and a speed (`keystone_core::ModelChoice`, saved as the session's `model`, `effort` and `speed`). Each is the provider's own value from its catalog: Claude's `value` such as `opus` or Codex's `model` such as `gpt-6-astra`, a catalog effort such as `high`, and a catalog speed. `None` sends nothing, so the provider's own configuration decides, or, after an earlier choice, what the conversation already has. Keystone lists no levels or speeds of its own.

**When.** The provider and account are chosen before the first Send and fixed from then on: `Store::lock_model` is written right before the first message goes to the provider, and a save failure refuses the send. `Session::started` is the one definition of "has sent"; a file saved before the lock existed counts as sent, since nothing proves it never launched. The model, effort and speed can change before and after the first Send (`Store::set_choice`). After it, a field that has a value cannot go back to Default, and the menu offers no Default row for it, while a field still at Default shows its Default row checked. Both providers keep an override for the rest of the conversation: Codex keeps it on the thread, even across `thread/resume`, and Claude's `effortLevel: null` falls back to the model's default, not the user's settings. So Keystone cannot honestly offer "your own setting" again.

**Changing the model.** A field at Default stays there. A chosen effort stays if the new model lists it, else becomes the new model's default effort. A chosen speed stays if the new model lists it. Otherwise, before the first Send the field returns to Default. After it, a field never returns to Default, since sending nothing would leave the provider on the old value, such as fast mode billing on with nothing shown: an effort becomes the nearest lower level the new model lists, ranked as the catalog ranks it, or stays when the new model lists no levels and so does not use it (Claude Code 2.1.316 launched on Haiku 4.5 with `--effort xhigh` sends no effort to the API), and a speed becomes the provider's standard speed (Claude's `fastMode: false`, Codex's `default`), which is sent. A model the catalog does not know keeps both. The button and the transcript note leave out an effort the model does not use and a speed the model does not list, and the button also leaves out standard speed.

**Saved before it is sent.** As for approval modes, the desktop saves with `Store::set_choice`, and only if that succeeds, and the session has a started connection, calls `Connection::set_choice`. A failed save shows "Model not saved." and changes nothing. A change applies to the next turn the provider starts, including one for a message already sent and still waiting to start it. It never changes a running turn, and a steer goes into the running turn as before. A change to a started session adds a muted line to the transcript, such as "Next turns: Sonnet 5.5 · effort high · Fast", from the catalog's labels. It is logged as `Entry::Note`, so it survives a restart, and handoff and second-opinion text leave it out. Builds before it skip the entry, as they skip any entry they cannot read.

**Path to the provider.** `Connection::send` carries the session's choice, and `Connection::set_choice` changes it at once. Each connection keeps every session's choice beside its approval state and gives it to the driver (`Command::Choose`) under the same lock, before the driver handles the session's messages, so a replacement process gets the latest one.

- **Codex.** `thread/start` and `thread/resume` carry the model. Every `turn/start` adds `model`, `effort` and `serviceTier` for each field that is set. A field that is not set is left out, never sent as `null`: Codex keeps what a turn sets for the thread's later turns, and `serviceTier: null` resets the tier to `default`. `turn/steer` carries none of them, so a steer that becomes the next turn uses the latest choice. A `turn/start` that asks for a model other than the one reported first sends `Event::ModelLost`, and `thread/settings/updated` reports the thread's new model. Codex sends that notification only to a client that opted into `experimentalApi`, which Keystone does on versions that take `show_ui`.
- **Claude.** Every launch, `--resume` included, passes `--model` and `--effort` for a chosen model and effort, and for a chosen speed `--settings '{"fastMode":true}'` or `'{"fastMode":false}'`: a stream-json process runs fast mode only with that flag-settings opt-in. The driver tracks the choice the process runs (launched with, then each change Claude accepted) and the one selected last, with a version like the permission mode's. Before the first message of a turn, if a set field differs, it sends `set_model` for the model and one `apply_flag_settings` with `effortLevel` and `fastMode` for the rest, and holds the turn's messages until Claude answers every one of them, beside the permission-mode gate. `set_model`'s answer names the model it resolved to, which is reported. A refusal of the latest selection fails the waiting turn with nothing written: "Claude Code refused the model change: …. Choose another model, effort or speed.". A request unanswered for 20 seconds fails it too, and the process is replaced before anything else is written to it. Steers are never held for a change. A replacement process launches with the latest choice, so it needs no change. The account decides whether fast mode runs: when the process asked for it and `system/init` reports a `fast_mode_state` other than `on` or `cooldown`, the driver warns once per process, and again only after the speed changes: "Claude Code did not turn on fast mode (…)". Fast is never shown as running.

**Reports.** The effective model is runtime data, never saved. Codex reports it with the thread reply and in `thread/settings/updated`, Claude in `system/init` and `set_model`'s answer. Both arrive as `Event::ModelReported`, kept per conversation in memory and cleared on `Event::ModelLost`, which a driver sends when the process or conversation that reported the model is gone (a Claude process exits or is replaced; the Codex app-server exits, or a thread cannot start or resume) or a Codex turn asks for another model. A failed turn keeps the report, since the provider is still there. So a requested model is never shown as running until the provider says so. After a restart every session reads "not reported yet" until its provider reports again.

**Catalogs** come from the providers, never from a list in Keystone, once per provider and conversation folder per app run until Retry (`Connection::request_catalog`, answered by `Event::Catalog`). Each answer is kept for the folder its request was made in. A session without a folder this version can use asks nothing and caches nothing; its menu says why. A layout helper connection refuses the request without starting a process. Codex answers `model/list` on the shared app-server; hidden entries are dropped, and its `isDefault` flag is not used as the default's label, since the configured default can differ. Claude lists `models` in its `initialize` answer, read from a throwaway `claude` in the session's folder that is closed as soon as it answers, on a timeout, or when the connection drops, following the permission-mode probe; its `default` entry becomes the model ID Provider default resolves to and is not itself a choice. A catalog entry carries what it is launched as (`ModelInfo::model`: Claude's `value`, Codex's `model`) and, for Claude, what that runs as (`resolved`), so a reported model can be shown by its catalog label. It also carries the model's efforts, in catalog order, its default effort, and its speeds, standard first:

- Claude: `supportedEffortLevels` when `supportsEffort` is true, no default effort, and Standard and Fast (the driver's `standard` and `fast`, for `fastMode` false and true) when `supportsFastMode` is true.
- Codex: `supportedReasoningEfforts`, `defaultReasoningEffort`, and, when `serviceTiers` is not empty, the standard `default` tier followed by each tier by its `id` and `name`. The deprecated `additionalSpeedTiers` is ignored.

**Choosing.** The composer button reads `<Provider>[ · account] · <model>`, then the effort when one is set and the speed's label when it is set and not the standard one. Once the session has sent, the effort and speed are muted, like a model the provider has not reported: they are what Keystone asks for, and Claude can still refuse fast mode for the account. Its menu shows a provider column before the first Send, the model column, and an Effort and Speed column with the session's catalog entry's choices: its model's, or on Provider default, the reported model's or the one the default resolves to. Without an entry, as on Codex's Provider default before the first Send, that column says "Choose a model to set its effort and speed". The palette's Next effort level (secondary-alt-e) and Toggle fast mode (secondary-alt-f) cycle the entry's efforts from Default to the first, and switch between its first two speeds; Next model (palette only) takes the next catalog model. Each takes the same save path as the menu, and says why it did nothing when the catalog has no such choice or has not loaded, asking for the catalog then. The quick composer chooses the model only.

## Claude Code in practice

Checked against Claude Code 2.1.300 on 2026-10-15. The driver is `crates/keystone-agent/src/claude.rs`. Its tests replay redacted recordings in `crates/keystone-agent/tests/fixtures/claude-2.1.300-*.jsonl`. `keystone-fake-claude` is a scripted stand-in for the UI and process tests.

- **Launch.** One process per session runs `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --permission-prompts host --permission-prompt-tool stdio`, plus `--permission-mode` for any approval mode but the default (on `--resume` too, and with the user's own mode for Provider settings after an override) and `--resume <session id>` once the session has one. It starts on the session's first message, in the project directory, and starts again with `--resume` after it exits or when the session's approval mode needs a new process (see "Approval modes" in section 6). `KEYSTONE_CLAUDE_PATH` chooses the binary. `--model`, `--effort` and fast mode as `--settings` are passed on every launch, `--resume` included, for what the session chose (section 11); with no choice none of them is passed, and with the default approval mode no permission mode either, so the user's own Claude configuration applies.
- **Turn tracking.** Each message carries a `uuid`, and Claude answers with `command_lifecycle` frames: `queued`, `started`, then `completed` or `cancelled`. A turn ends when its latest `result` is in and every message sent during it has finished. A message cancelled before it started gets no `result` at all, so Stop right after Send ends the turn when the cancellation arrives. Each message's start is tracked, so if Stop cancels a queued follow-up after an earlier message's successful `result`, the turn ends as stopped, not completed.
- **Steering needs lifecycle frames.** Without them a steer's aborted first `result` would end the turn while the steer still ran. Keystone detects support from the stream itself: any `command_lifecycle` frame, or `msg_lifecycle_v1` in `system/init`'s capabilities. Claude 2.1.300 sends `queued` as soon as a message arrives, before `init`. Until one of these is seen, or when `init` lacks the capability, a message sent during a turn is refused: the composer keeps the text and the transcript shows the reason itself. A message sent while the previous one is still waiting on the worker, or for Claude to start, counts as such a steer. The version number is not used, because the capability is what the driver depends on.
- **Items.** Text and thinking blocks stream from `stream_event` deltas and complete from the whole `assistant` block. `tool_use` starts a tool item: `Bash` becomes a command, `Edit`, `Write`, `MultiEdit`, and `NotebookEdit` become file changes, and anything else a named tool. The matching `tool_result` completes it with capped output. A failed command's exit code is read from Claude's "Exit code N" prefix. A denied call shows as not run. Subagent traffic (`parent_tool_use_id` set) is not shown.
- **Questions.** `AskUserQuestion` and `elicitation` are questions; see "Questions" in section 6.
- **Approvals.** `can_use_tool` becomes an approval. Allow sends the input Claude asked about back unchanged; Deny sends a denial message. `control_cancel_request` withdraws one, and a later answer to it is not sent. Claude's request IDs are only unique within its process, so Keystone's IDs include a per-process seed, and an answer from before a restart never reaches a new request with the same ID. Any other control request gets an error response.
- **Stop.** `interrupt` with `cancel_queued: true`, so steers Claude has not started are dropped too. Claude completes the cut-off text block itself, so the partial reply is kept.
- **Errors.** A failed `--resume` produces a `result` before `system/init` and then exit 1. The turn fails with "Could not resume this Claude Code conversation", and Keystone never starts a fresh conversation in its place. A signed-out Claude sends a synthetic assistant message with `error: authentication_failed`. Keystone does not show it as a reply; the turn fails with a sign-in message. A missing or unstartable binary fails the turn from the worker with the path and the OS error, shown in the session's transcript.
- **Version and capability safety.** The connection checks `--version` before launching a conversation or catalog probe. See [Provider compatibility](#provider-compatibility). Versions without lifecycle frames or queued-message cancellation run one message per turn and cannot be steered. Thinking text is kept only when Claude sends it; with summarized thinking off it is empty and hidden.
- **Not built yet.** Idle processes are not stopped, so each Claude session keeps its process until Keystone quits. Background-task turns, hook events, and `/` commands are not specially handled. Reconciliation of Claude's transcript after a crash is not built.

## Provider compatibility

`crates/keystone-agent/src/version.rs` is the compatibility policy: each provider has a minimum supported baseline, a highest connect-tested version, a conservative known-incompatible ceiling, and a queued-cancellation fallback. The current ranges include Claude 2.1.300–2.1.301 and Codex 0.162.1–0.163.0. Full turn recordings remain at the lower endpoints; the upper endpoints were checked with the real installed CLIs on 2026-10-19 using `--version` and initialize only, with no user messages or inference. The redacted connect frames are `tests/fixtures/provider-connect-probes.json`. The scripted cases in `tests/fixtures/provider-versions.json` prove Keystone's handling, not additional real-provider turns. Widening the range requires an observed probe or recording and explicit verification scope.

The host runs the selected executable's `--version` on the command worker, outside connection locks, before starting the protocol. The probe uses the existing process-tree teardown and a two-second response deadline. Canonical Claude and `codex-cli` output or bare `major.minor.patch` numbers are accepted; prereleases, custom builds, unsuccessful probes, and unknown output are untested. Untested versions continue with a quiet, muted notice in the existing status area, naming the detected output, minimum baseline, and tested range. It appears once per distinct version/report per provider connection in an app run, not once per session or reconnect. The first notice survives successful turns and is cleared by a changed compatibility result or provider choice; it is not saved in the transcript or preferences. Restarting Keystone resets this run-local warning deduplication. No user prompt is sent by a version probe. Checks deliberately repeat for a new process instead of caching a path indefinitely, so replacing/upgrading the CLI is detected before another prompt.

Only releases known to lack a required protocol are rejected before a turn starts. Claude Code 0.2.9's published npm executable has no `--input-format`, stream-json or stdio permission-control support ([published package](https://registry.npmjs.org/@anthropic-ai/claude-code/0.2.9)); the policy rejects it and earlier versions. Codex 0.20.0's CLI has no `app-server` command ([tagged source](https://github.com/openai/codex/blob/rust-v0.20.0/codex-rs/cli/src/main.rs)); it and earlier versions are rejected. Versions between these ceilings and the tested range are **not** asserted incompatible or certified compatible: they warn and attempt the existing handshake. Installation errors keep the executable path and OS error, and incompatible-version errors name the missing protocol and suggest installing a tested version.

Codex probes optional `optOutNotificationMethods` support in initialize regardless of tested-range membership. Acceptance is the observable capability signal (the real 0.163.0 answer has no explicit capability list). A rejection of the optional parameters retries a plain initialize once, before any thread or prompt is written; extra notifications are then ignored. Other handshake failures fail queued work explicitly. When widgets are on (Codex 0.163.0 and later), initialize opts into `experimentalApi`, because `thread/start.dynamicTools` requires it; the opt-in covers the whole app-server connection. Otherwise no experimental API is opted into. See [widgets.md](widgets.md).

Once Codex answers `initialize`, Keystone sends `initialized`, then the requests that waited for it, then `account/rateLimits/read` with `excludeResetCreditDetails: true` as request `keystone-rate-limits`, outside the numbered requests. Nothing waits for it and it is never timed. Every app-server asks, including one started for a crash-recovery read or an import listing, so Codex may then refresh its own login as it does whenever it is used. A successful answer reports the windows of `rateLimits` and each bucket of `rateLimitsByLimitId`, read like `account/rateLimits/updated`, as one `Event::Usage`; a window both views carry is reported once. A bucket other than `codex` with no `limitName` is left out rather than shown under its raw ID. `accountId`, `planType` and credits are not read. A window an `account/rateLimits/updated` already reported in the process is left out, since the read was asked for earlier. An error, such as Codex 0.163.0's "codex account authentication required to read rate limits" for a home with no login (seen in a no-inference probe), an older Codex that does not know the method, or any shape Keystone cannot read reports nothing.

Claude's initialize answer does not advertise lifecycle or queued cancellation on the real 2.1.301 install, and `system/init` arrives only after a user message. So tested-or-newer versions keep the existing queued-cancellation default until that turn-time handshake can override it; unknown/older versions wait for the actual advertisement. `interrupt_cancel_queued_v1` in `system/init` enables the optional interrupt field; its absence omits it and refuses steering with an explanation, retaining the composer text. `msg_lifecycle_v1` or observed lifecycle frames remain required too. Newer-than-tested versions keep capabilities rather than being downgraded by a version warning. Hook events before initialize are tolerated. All IO and deadlines live in the connection/host; drivers receive flags and remain pure state machines.

## Images

Attached images go to each provider in its own form. Claude Code gets the message as a list of content blocks: the text first (left out when the message has only images), then one `{"type":"image","source":{"type":"base64","media_type":…,"data":…}}` block per image. The connection reads and encodes Keystone's copy on the session's worker before it takes the shared lock, so a large image never holds up other sessions. A message without images is still sent as plain string content. Codex gets `{"type":"localImage","path":…}` items after the text item on `turn/start` and `turn/steer`, with the absolute path of Keystone's copy, and reads the file itself. A [no-inference probe](../research/image-input-probe.md) of Claude Code 2.1.301 and Codex 0.163.0 against a refusing local API confirmed both accept PNG, JPEG, GIF and WebP on a new turn: Claude Code passes them through with their media type and shrinks large ones, and Codex converts GIF to PNG. Neither refused a type, so Keystone has no per-provider fallback; a later refusal shows as the provider's own turn error. Images in a Codex steer use the same item but were not probed against the real CLI.

Claude Code reads an `@path` mention itself only in string content: in a message with images the mention reaches the model as plain text, which it may read with its own tools, as Codex does. Send refuses, and keeps the draft, when a copy is missing or cannot be opened. A copy that becomes unreadable after that check stops the message before anything is written to Claude, with its path and the reason: a new turn fails, and a steer is refused with a warning while the running turn goes on. The message stays in the transcript, so the image has to be attached again.

## Limitations

These are the costs of the choices above, and what would make each one wrong.

1. **Claude's control protocol has no published spec.** Keystone uses the same flags and messages as the official SDKs, which lowers the risk but does not remove it. A Claude Code release can change behavior with no notice to third parties. The official SDKs absorb that because they ship in lockstep with the CLI; Keystone does not. Mitigation: capability detection, a tested version range, recorded fixtures, and the opt-in live check. If this proves too fragile, the fallback is a small Node helper around the official Agent SDK, as T3 Code does, at the cost of a Node runtime.
2. **Pure drivers still need time-based behavior somewhere.** Interrupt escalation and idle shutdown need timers. They live in the process host, not the drivers. A driver cannot say "no answer within 3 seconds", which Zeron uses after a stop request. Keystone accepts a stop as pending until the provider ends the turn, and offers a forced stop after a visible delay.
3. **One shared Codex process is one failure domain.** If the `codex app-server` process itself dies (a Codex bug, out of memory, or killed), every Codex turn running at that moment stops. Conversations are not lost: Codex has saved them, and Keystone restarts the process and resumes each thread, but the user has to resend the interrupted turns. Failures inside a session, such as a failed shell command, a crashed MCP helper, or a model error, stay in that session. A hang is worse than a crash, because Keystone must detect it before restarting. One process also means one global Codex configuration: anything that differs per session must go through `thread/start` and `turn/start` parameters. If crashes prove common, Keystone can cap threads per process or give each project its own app-server.
4. **Claude memory scales with sessions.** At 256 MB each, ten active Claude sessions use about 2.5 GB. Idle shutdown would limit this, at the cost of a fresh process start on resume, but it stays off until a Claude profile's quiescence is proven ([Idle shutdown](#idle-shutdown)), so today every started Claude session keeps its process until Quit or an exit.
5. **Keystone's log is a partial copy.** It stores completed items and capped tool output, not every provider event. Detail the provider keeps but Keystone does not render (for example raw thinking signatures or hook events) is only in the provider's own transcript. Claude deletes transcripts after 30 days by default, so for old sessions Keystone's log may be the only record left, and resume will fail.
6. **Two copies can disagree.** If the user also continues a session in the plain CLI, the provider's transcript moves ahead of Keystone's log. Reconciliation fills the gap on resume, but for Claude it reads an internal format that may have changed. Keystone must show when reconciliation was partial.
7. **Coalescing hides per-token timing.** Rendering once per frame is invisible at 60 Hz, but Keystone keeps no record of when each delta arrived. A future "replay this turn" feature would need provider timestamps.
8. **Capped tool output loses the middle.** A 10 MB build log keeps its first and last 32 KB. That covers most needs; the full output exists only in the provider's records, if anywhere.
9. **Not using the official SDK has a policy dimension.** Anthropic's terms are written around the Agent SDK. Driving the CLI directly with the user's own login matches the allowance for the unmodified binary, but it is a judgment call, and Codex says app-server authentication was never permitted for commercial services. Both are fine for a local, personal tool and need review before any commercial release.
10. **Approvals depend on the chosen mode.** In a manual mode, sessions pause until the user answers, and the inbox must make that obvious. Auto modes avoid the pauses. Keystone never auto-approves on the provider's behalf; it changes the provider's own mode, so the provider's safety checks still apply.
11. **Linux first.** Process-tree teardown through `/proc` and the measurements above are Linux-specific. See the platform section below.

## Platforms

Keystone targets Linux first, with macOS and Windows later. GPUI supports all three. The provider layer keeps platform code in one module of the process host so the drivers never change.

| Concern | Linux | macOS | Windows |
| --- | --- | --- | --- |
| Kill a whole process tree | Own process group, then descendants from `/proc` | Own process group, then descendants from `libproc` | Job object with kill-on-close; this covers every descendant |
| Find `claude` and `codex` | `PATH`, plus common install directories | Apps launched from Finder do not get the shell's `PATH`; read the login shell's `PATH` once | `.cmd` and `.ps1` npm shims, `%APPDATA%\npm`, and native installers |
| Graceful interrupt | Protocol interrupt, then SIGINT | Same | Protocol interrupt, then terminate; there is no SIGINT for pipes |
| Provider data | `~/.claude`, `~/.codex` | Same | `%USERPROFILE%\.claude`, `%USERPROFILE%\.codex` |

Other platform work outside the provider layer: the workspace store syncs its parent directory after writes (KS-001), which Windows does not allow, so that step needs a Windows path. Native verification uses nested Sway and is Linux-only; macOS and Windows need their own checks. There is no CI yet. A build and test matrix on all three platforms should come before the first non-Linux release.

## Signing in

Keystone does not handle credentials by default. It uses whatever login the user's `claude` and `codex` already have.

OpenAI's **Sign in with ChatGPT** is an option for Codex. The user signs in through the browser and grants "ChatGPT plan usage". Keystone receives OAuth tokens and passes the access token to `codex app-server` in an environment variable, with a `model_provider` configuration pointing at the Responses API ([codex app-server guide](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)). It is available now for open-source projects and personal projects that run locally; paid or hosted apps join a waitlist ([cookbook, 2026-09-28](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)). It needs a Plus or Pro plan.

What it would change:
- Users would not need to run `codex login`, and their usage appears under ChatGPT settings for the app.
- Keystone would hold refresh tokens, so it must store them in the OS keychain and own the browser sign-in flow (PKCE, a loopback callback, and an installation host ID). OpenAI's devkit is TypeScript, so Keystone would implement this in Rust.
- A new access token requires restarting `codex app-server`. With one shared process, Keystone starts a new process with the new token and moves each thread over when its turn ends, so no running turn is cut off.
- `model/list` returns a bundled catalog in this mode, so a model is confirmed only by a successful turn.

Claude has no equivalent. Anthropic does not allow third-party apps to offer claude.ai login, so Claude always uses the user's own `claude` login.

Recommendation: ship with the existing CLI logins, and add Sign in with ChatGPT as an optional Codex account choice once the core works. It is also the sanctioned path if Keystone is ever distributed.

## Accounts

A provider can have several accounts, for example two Claude Max subscriptions. Each added account is a folder that holds that provider's own config: Keystone starts every process for the account (the CLI, its `--version` check, and model and permission probes) with `CLAUDE_CONFIG_DIR` or `CODEX_HOME` set to it. It never changes `HOME`, so the provider's native tools, skills and other config stay where they are. For an added account Keystone also removes that provider's inherited credential variables (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` for Claude; `OPENAI_API_KEY` and `CODEX_API_KEY` for Codex), so one account can never run on another's key. Claude accounts also drop `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY`, which would route them to a cloud provider's credentials instead; `ANTHROPIC_BASE_URL` is kept as routing configuration. The default account is the inherited environment, unchanged, and every session saved before accounts existed uses it.

Each Codex account gets its own `codex app-server`; Claude sessions already run one process each. Model catalogs are kept per account. A session's account is chosen in the composer's model menu, which lists accounts only once one has been added for that provider, and is fixed at the first send, like its provider and model. Moving a conversation to another account is a later handoff feature.

Keystone never signs anyone in. Settings → Accounts shows the command to run in a terminal, such as `CLAUDE_CONFIG_DIR='/home/me/.claude-work' claude auth login` or `CODEX_HOME='/home/me/.codex-work' codex login`. Adding an account creates its folder with mode 0700; a folder that already exists keeps its permissions. Folders are compared after resolving symlinks and saved as their real path. Account folders may not overlap each other or the default homes, and an account in use by a session cannot be removed; removing one keeps its folder.

Probes on 2026-10-19 with Claude Code 2.1.301 and Codex 0.163.0:
- Claude creates a missing `CLAUDE_CONFIG_DIR`; Codex exits when `CODEX_HOME` does not exist, so Keystone creates the folder when the account is added.
- With the variable set on every spawn, neither CLI wrote under `$HOME`.
- Signed out, Claude's `initialize` reports `account: {tokenSource: "none", apiProvider: "firstParty"}`, and Codex's `account/read` returns `{account: null, requiresOpenaiAuth: true}`. Signed in, Claude reports email, organization and `subscriptionType` (for example "Claude Max"); Codex reports email and `planType`. Keystone never shows email or organization; a plan name is acceptable as a label.

## Crash recovery

A turn Keystone lost track of is checked against the provider's own record, read-only. That covers a turn still open when Keystone was killed, and a provider process that exited during a turn while Keystone ran. A provider exit is logged with the turn it ended, after that turn's other events even while the history is still loading, so if Keystone dies before the check is saved, the next start checks again. Recovery never writes to a provider's store and never resumes, starts or steers a turn. It never answers an approval and never resends anything. It only runs for the session's own account: Claude reads under that account's `CLAUDE_CONFIG_DIR`, and Codex asks that account's `codex app-server`.

- **Claude** finds `<session>.jsonl` in any folder under the config dir's `projects/`, without depending on how Claude escapes the working directory. The session ID is validated and every path is resolved. The file is opened without following a final symlink, and the opened file itself must be a regular file inside `projects/`, so a path swapped after the scan is not read. A read covers at most the last 64 MiB and the last 20,000 records, found by scanning back from the end; a line over 1 MiB is skipped as malformed. A file that changes during the read is reported unstable. A cut-off last line is a torn tail and the records before it still count. A different `cwd` is an identity mismatch, and two matching files count as a branch. A compaction boundary has no `parentUuid` and links back through `logicalParentUuid`, which the chain follows. Claude's format is internal and changes between versions, so the reader is pinned by synthetic fixtures rather than relied on.
- **Codex** sends `thread/turns/list` with `limit: 20`, `sortDirection: "desc"` and `itemsView: "full"`. If that fails for any reason, including Codex's -32600 for a method it does not know or a refused `full` view for a paginated thread, Keystone asks `thread/items/list` for the newest 200 items instead. Each comes wrapped with the ID of its turn, so items keep their turns, but no turn end is known. An entry with no item, or an item with no ID, is counted as unreadable. Neither request opens or resumes the thread, and neither loads the whole thread; both are bounded by count, not bytes, and the shared transport reads each reply whole.

Both readers produce one neutral snapshot of items and turn ends. When a read covers only the newest part of a long history, that is dropped if the part reaches back to what Keystone shows, and reported otherwise. A pure `reconcile` compares the snapshot with the restored rows by item ID, off the UI thread. It replaces an unfinished row when the provider holds more of it, and inserts items the log never saw after the row they follow. Each operation names the exact old value it replaces, so a stale batch never overwrites a newer row. Reused IDs, a different order, no common point, text that contradicts a row, or another identity are conflicts: Keystone keeps its own rows and reports the conflict. Batches are capped at 4 MiB, measuring each operation once; anything dropped, including a single operation too large to save, is reported as truncated.

The result is saved as one recovery entry in the session log through the log worker. Its rows are shown at once, and the next message stays held until the entry commits, so a save failure leaves sending held with Retry. A check that never saved runs again on the next start; one that saved is never checked again. A restore applies each saved batch where it sits in the log, to the rows logged before it, so later starts show the same rows with no new check. A tool call with no recorded result, and an incomplete text block, are shown as **Interrupted** with no recorded result, never as failed or successful. Approvals from the old process are dropped, because their request IDs cannot be answered. The current model stays "not reported yet".

The report counts recovered messages, tool calls and extended rows, and lists every limit. When the provider recorded how the turn ended, the report says so; otherwise the outcome is unknown, which holds for a provider that exited mid-turn too. A full recovery lets the next message go at once. A partial or conflicting recovery, or one that could not run (a missing store, no saved provider ID, a check that took longer than 5 seconds), holds Send. A conversation with a saved provider ID also waits for its history before sending, since the history decides whether a check is needed; the card says so. If the history has not arrived within 5 seconds, or cannot be read, the card offers Continue, after which the message goes. The card above the composer says why, and **Continue with available history** (Ctrl+Shift+Enter) lets the next message go unsent and keeps the draft. **Retry** (Ctrl+Shift+R) checks again, for example to add what a truncated recovery left out, or saves again after a save failure. A retry that finds nothing new saves nothing and keeps the earlier report. Both are in the command palette and reachable with Shift+Tab from the composer. The hold is not saved, so a restart before sending shows it again. Claude store reads run on at most two threads of their own, so a stuck disk holds up only its slot, and a read abandoned at its deadline that never started is dropped.

## Importing sessions

Import sessions… lists the conversations a provider account already keeps for the window's project folder and imports one as a new session. It uses the crash-recovery readers and their bounds, so it is read-only in the same way: it never writes to a provider store, and it resumes, starts or answers nothing until the user sends.

- **Claude** lists each `projects/*/<id>.jsonl` under the account's config dir whose first main-chain record, within the file's first 1 MiB, names the folder as its `cwd`, under any name for it: a symlink such as macOS's `/tmp` for `/private/tmp` matches. Each of the newest 50 is then read as recovery reads it, which gives its first message as its title and its turn count. A store the reader cannot follow, such as a branched one, is not listed.
- **Codex** asks the account's app-server for `thread/list` with the folder as `cwd`, sorted by `updated_at`, at most 50, from the `cli`, `vscode`, `exec` and `appServer` sources, with `useStateDbOnly` so Codex reads its index rather than scanning its logs to repair it. A thread Codex has not indexed yet is not listed. It then counts each thread's turns with `thread/turns/list` and `itemsView: "notLoaded"`, up to 1,000. A thread with no turns is not listed; one Codex cannot count, as on an app-server without turn pagination, is listed without a count. Codex matches `cwd` exactly, so a thread recorded under another name for the folder is not listed. The import reads the newest 50 turns as recovery does, with its `thread/items/list` fallback.

The new session holds the provider's ID as its `provider_thread` and the chosen account, and counts as started, so its next message resumes the conversation like any restored session, and the provider records it in its own store as usual. Its log starts with the newest 50 turns, as completed turns, after one line saying older messages weren't imported when there are more. A conversation that a session already continues, under the same provider ID, cannot be imported again; the list marks it Imported and opens that session. A read that finds nothing to import, or a conversation that no longer matches what was listed (it branched, or now names another folder), is refused with "Not imported. It changed since it was listed." The list is bound to the folder it listed: leaving the project or closing the window closes it, and answers still on their way are dropped. A later crash recovery in an imported session compares only from its oldest imported item, so the history left out is not reported as differing.

## Idle shutdown

Keystone can end a Claude chat session's process after 10 minutes of **proven** idle and start it again, resuming the same conversation, on the next Send. It is **off by default** for every Claude profile, so every started session keeps its process. The machinery ships behind that default and is exercised only by tests and scripted providers; the gap is evidence, not code.

**Why off.** Idle eviction is only safe when Claude itself promises that nothing will start between the proof and the kill. For Claude Code 2.1.300–2.1.305 nothing published does, and 2.1.300, 2.1.301 and 2.1.305 show the opposite (TOB-44; probes of the real binary with Keystone's default chat launch flags (no `--permission-mode`, `--model` or `--resume`), offline in a network namespace with a disposable `CLAUDE_CONFIG_DIR`, no credentials and no user message, and in most scenarios `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` to observe state changes, so every turn below ended at "Not logged in" with no tokens spent):

- **What the check reads arrives in the expected shape.** From an idle process, a repeated `initialize` answers with `session_state: idle` inside its `response` (a field the binary's own schema marks internal, a snapshot at connect time) and empty `pending_permission_requests` and `pending_user_dialog_requests` beside it, then an empty `background_tasks_changed`. It leaves the user's hooks, the configuration of an MCP server set after start (offline, so a failed one; a live connection was not tested) and a changed permission mode as they were, and does not run `SessionStart` again. The first `initialize` gets no snapshot. No probe got a non-idle `session_state` (that needs a turn in progress when the check arrives), so nothing shows the field reports one; it reported `idle` while an `asyncRewake` hook was still running. `session_state_changed` is opt-in through `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` (Agent SDK 0.2.83), which Keystone does not set; with it set, the probes saw it only around turns. The check does not depend on it.
- **What it cannot see starts turns.** A scheduled task saved in the project's `.claude/scheduled_tasks.json` (where Claude keeps tasks when it cannot fetch feature flags, as offline; it stands in for tasks a real turn would create with `CronCreate`, `ScheduleWakeup` or `/loop`, which no probe could make without inference) started a turn every minute in a process that had just passed every part of the check, and the check passed again after the last of them: neither the `initialize` answer nor the task snapshot lists scheduled tasks (Claude reports them, as `session_crons`, only to `Stop` and `SubagentStop` hooks). A task file written after launch did not fire within 100 seconds, and `CLAUDE_CODE_DISABLE_CRON=1` stopped the saved one. An `asyncRewake` hook from user settings exiting 2 started a turn with no message from Keystone; Keystone's open-hook rule happened to catch that one, because its `SessionStart` reported `hook_started`. With `remoteControlAtStartup` in user settings, the `-p` process's answer reports `remote_control_auto_enable: true`, the CLI's own resolver saying Remote Control should start; whether a `-p` process then connects was not tested offline, and the docs describe the setting only for interactive sessions. The published docs add cross-session `SendMessage`, background-task completions and quota auto-resume as ways an idle session starts a turn, and nowhere promise that a quiet headless process stays quiet.
- **No conditional shutdown was found.** No documented control request, setting or flag ends Claude only if it is still idle, and among the 88 control request names the binaries test for (the same in all three), `end_session` is the only one named for shutting down. `end_session` (present, undocumented) ended an idle process in 0.02–0.03 s, and its handler in the binary aborts a running turn and discards the queue first, so it is a SIGTERM with extra steps rather than a promise. `CLAUDE_CODE_EXIT_AFTER_STOP_DELAY` exits on Claude's own idle timer, set at launch; what it counts as idle is undocumented and was not probed.

Killing such a process silently stops the work it would have done: a session's scheduled tasks fire only while it runs, and documented resume restores only some of them. So no profile is enabled. Turning off scheduled tasks, Remote Control or the user's hooks to make one eligible would strip the provider's own configuration, which Keystone does not do. SIGKILL also leaves Claude's own session marker (`sessions/<pid>.json` under the config directory) behind. A local timer cannot make up for that, and no longer grace period, quiet snapshots, EOF or `/proc` check stands in for the proof. Every gap fails closed: a missing field fails the check, and a missing frame leaves the process running.

**What would change it.** Any one of these, shown against the real CLI for its version and launch flags without real inference, would let one profile turn eviction on: a conditional shutdown Claude performs only if nothing is running, queued, scheduled or waiting on a hook, answered atomically against new work; or a quiescence answer that also lists scheduled tasks, wake-ups, Remote Control and channel connections and async hooks, so that their absence is a statement rather than silence, together with a fence, taken before that answer is computed, that holds new work (a fired task, cross-session or remote input) until Keystone has ended the process or let it go. The store needs the same receipt with real turns: a synthetic turn's assistant message (its ID and text) was in the store when SIGKILL ended the process 10 seconds later, but no fuller comparison was made and a turn with tools and streamed text was not tested. The probes and the evidence matrix behind this section are summarised on TOB-44 in Linear.

**What proven idle means.** The connection tracks, per process, everything the driver observes and every message admitted, as an activity epoch. A process is a candidate only when it is a chat launch with a conversation ID; it finished starting and confirmed its permission mode; nothing is queued, held, being replaced or reading approval settings; no turn, approval, tool call, Keystone control request other than `get_usage`, or hook (`hook_started` without its `hook_response`) is open; Claude has reported no session state but `idle`; its own last task snapshot, if any, is empty, ambient tasks included; and nothing Keystone could not read or attribute arrived since the last passed check. Task and hook frames count before the subagent display filter, so a subagent's work blocks too. A completion edge such as `task_notification` clears nothing; only a snapshot replaces the set, and only the conversation's own: no parent tool call and the conversation's session ID. The same goes for `session_state_changed`. A subagent's snapshot or state, another session's or an unnamed one is activity that proves nothing, even when empty or `idle`, and like an unreadable safety frame it keeps the process from being offered until a check passes. It does not stop the check itself, which is the refresh that clears it. Then Keystone sends a repeated `initialize` on the session's own worker. It passes only on a success answer whose `response` reports `session_state: idle`, with empty `pending_permission_requests` and `pending_user_dialog_requests`, followed by an empty `background_tasks_changed` for that request. Absent fields, a non-idle state, a pending approval or dialog, any task, a refusal, or no answer within 2 seconds leave the process running with its reason, and nothing retries on a timer: the next activity starts over. A hook that reported `hook_started` and never its `hook_response` keeps the process for its lifetime, since no snapshot of hooks exists to refresh it. The check's own answer and snapshot, keep-alives, rate-limit notices and the `get_usage` answer are not activity; everything else is, including frames Keystone does not recognise. Activity abandons a check in flight, whose request stays open until Claude answers, so the next check waits for that answer: it is activity, and the snapshot after it is not. A check's 2-second timeout ends only that check, never the one at the interval's end.

A passed check arms one deadline on the connection's single scheduler thread, measured on a monotonic clock. Any activity makes it stale. When it comes due, the check runs again; a pass then offers the process to the app as `Event::IdleCandidate`, queued behind the session's earlier events.

**Saving first.** The app accepts a candidate only once every earlier event is applied, the conversation ID it names is saved in the workspace and synced, the history is loaded, no turn runs, and the conversation is being saved. While workspace changes are still being saved, the candidate waits and is considered again once they are on disk. It then asks the log for a checkpoint of everything queued so far. A failure anywhere keeps the process, and the app tells the connection why, which reports it as the reason the process stays until its next activity. Only a saved checkpoint confirms the candidate back to the connection.

**Ending.** The confirmation runs on the session's worker and re-checks the generation, epoch, conversation and every blocker. A tree holding a process Keystone may not signal, such as a command run through `sudo`, keeps its process: SIGKILL could not reach it, where Quit's SIGTERM can, through its parent. It removes the process from routing and marks the session not running for Keystone's tools under the lock, queues `ModelLost`, then ends the process tree off the lock (`Process::end`). Nothing gets SIGTERM, since a handler could start a process outside the tree as it exits. The tree is frozen with SIGSTOP instead, rescanning after everything found has stopped until a scan finds nothing new, so no process forks past the scan; then all of it gets SIGKILL, and the worker waits, however long that takes, until the leader and every process found have exited. Claude so gets no chance to write anything on its way out; that its store already holds the whole conversation after the interval is one more thing enabling a profile must establish (see **What would change it**). A process that had already left the tree before eviction began, such as a daemon a tool started and detached, is out of reach, as it is on Quit. A message sent meanwhile waits on the same worker and starts the successor once, after the old tree is gone. A stale confirmation ends nothing. Eviction writes no turn end, failure, recovery request or unread change, and leaves the saved thread, approval state and requested model alone.

**Resuming.** The next Send runs through the usual gates, crash recovery's included: a session with a recovery report or unloaded history still waits. Eviction itself never starts a recovery check, because nothing was lost: the turn had ended and was saved. The process starts as any resume does, with `--resume` and the same saved folder, the requested model, effort and fast-mode flags (none for a field at Default, whatever the old process reported), the approval flags, and the session's own account's `CLAUDE_CONFIG_DIR`. The model shows "not reported yet" until the new `system/init`. A resume Claude refuses is the existing "Could not resume" error, never a fresh conversation. Approval IDs carry the process's seed, so an answer to an approval from before eviction answers nothing after it.

**Agent-launched sessions.** A child an agent launched is evicted under the same rules. While dormant, `session_send` returns `busy: The target is not running`, as for any idle target, since sends only steer; `session_read` and `session_wait` answer from Keystone's own rows without starting it; `session_interrupt` does nothing. A child resumes when the user, or a later launch-and-send, sends it a message.

**Out of scope.** Codex, the catalog and permission probes and the layout helper are never evicted. There is no setting and no indicator. Close and Quit are unchanged.

Debug builds take `KEYSTONE_TEST_CLAUDE_IDLE_MS` to turn eviction on with a short interval, for scripted providers in native runs, and only while `KEYSTONE_CLAUDE_PATH` names the Claude to run. Release builds ignore it. A real Claude passes the check too, so pointing that path at one evicts it on the same unproven terms.

## Terms

Keystone runs the user's own unmodified `claude` binary and never handles their credentials. That matches Anthropic's allowance for "an end user … signing in to the unmodified Claude Code binary with their own Claude subscription". The product name must not include "Claude". OpenAI says local and open-source apps can keep using app-server authentication, but it has "never been permitted for commercial or hosted services". Revisit both before any commercial release.
