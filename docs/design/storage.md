# Workspace storage

Keystone uses one bundled SQLite database for workspace metadata and neutral conversation entries. `Store` applies each change to its in-memory read model at once and queues its commit on the database's writer thread. `Logs` runs transcript commits on its existing worker thread. Neither adds an async runtime.

## Transactions and events

`events.sequence` is a global, monotonically increasing committed cursor. Events contain complete session or workspace replacements and neutral log entries, not streamed deltas. Update/delete triggers make the event table append-only. `sessions`, `workspace` and `log_entries` are the projections the application reads. Workspace metadata excludes session bodies, so changing one session does not serialize every session into the event log.

The event history retains previous saved drafts and session values, even after their projection changes. No event compaction or retention policy is implemented yet, so database size grows with saves. Treat the entire database and its backups as private history, not only the visible transcript.

A workspace transaction obtains the SQLite writer lock, compares the stored workspace revision with the one Store last loaded or committed, appends events, upserts projections and commits. Store has already published the change in memory by then. A stale writer returns a reload-required error without overwriting the newer workspace. Retrying cannot clear that error, so it is final for the Store: its queued changes are dropped, later changes fail the same way, and the status line keeps showing it. Transcript commits do not advance the workspace revision. Each queued transcript record carries a stable event key; retrying an uncertain successful commit cannot duplicate it.

All disk connections use WAL, synchronous=FULL and foreign keys. Each database file has one writer thread per process, which owns the only write connection: opening the same file again joins the live writer instead of starting another. Writes run on it one at a time, in the order they were queued, so the app's Store and log worker never contend with each other. The connection stays open while the database is in use, so a closing reader is never the last connection and never checkpoints the WAL or leaves the next opener to rebuild its index while writes wait. When its queue empties, the writer copies the WAL into the database file and empties it before it answers the last write, as the last connection to close used to; a reader holding the WAL makes it try again every 100 ms while idle. So an idle database file is complete on its own, and a file that replaces it is never read through its old WAL. Before each write it reopens the connection if the file was replaced or removed, or this process can no longer write it, and after any failure other than busy, so path replacement and permission repair still work. While this process cannot write the database's folder it refuses the write, as a fresh connection would open the database read-only there. A write waits up to 2 s for the writes queued before it, a guard against a hung writer; one that has not started by then is withdrawn and reported busy. SQLite's busy handler gets 100 ms for a lock another process holds. A read first waits for the writes queued before it, then uses an independent read-only connection, so it sees every change issued before it. In-memory Database/Store constructors serialize on their own connection without filesystem access or a writer thread, and commit inline. Store never waits for its commits, so a slow filesystem syscall or a large transaction delays the save, not the app.

## Durability, retries and Quit

A successful FULL commit is the database durability boundary; no checkpoint is required for success. A conservative parent-directory sync also confirms database/WAL directory entries. A Store change returns as soon as memory has it; an error from it means only that the change was refused in memory. The writer commits each change as its own transaction, in order, then confirms them with one directory sync. When a commit fails, nothing of it is written and memory keeps the change. The newest snapshot stays queued, and since it holds every unsaved change, the next try commits them all in one transaction. The next change, `Store::retry` or `Store::flush` tries again; changes queued behind a failure are tried once, by the newest. A commit whose directory sync failed retries only the sync, without repeating the SQL transaction. A revision confirmed once remains confirmed through unrelated later failures. The app shows a failed save as one status line until a retry saves it: "Not saved. {error}", or, as a warning, "Saved, but not confirmed on disk. {error}" when only the directory sync failed. A message goes to a provider only once every change queued before it is on disk, which covers the saves it depends on: an approval override, the model lock and a cancelled continue, including those an earlier refused send left queued. The send retries a failed save, waits up to 2 s, and is refused, keeping the composer text, if the changes are still not on disk. A result is saved as delivered first and goes from a later pump once that save, and every change queued before its send, is on disk, so no pump waits for it; Quit saves a result not yet sent as ready again. Quit waits for every Store change to be saved, and refuses with one line, "Not quit. {reason}", while one cannot be, except changes a stale writer left unsaved, which no retry can save.

Busy/locked, full-disk, read-only, permission, open and I/O errors are visible recoverable errors. Transcript failures retain their batch and stable keys; a later append or flush retries it. A committed prefix whose directory barrier failed retries only that barrier, without SQL write access. While that barrier keeps failing, later entries still commit in their own transaction behind it, so SQLite holds them if the process dies. Budget bytes retire only after durability is confirmed. The 16 MiB admission budget, shared by every session, bounds retained bytes, apart from gap markers and the boundary reserve described below. An item or approval over a quarter of the budget keeps both ends of its text with a note of what was left out; other fields are never shortened, and such a cut is not counted as loss. An entry that still does not fit the room left is terminal loss: it is surfaced immediately, and a count-bearing gap marker is queued in its place, at the rejected entry's own position, and saved like any entry, so it survives a crash before Quit. Turn boundaries and provider exits are never rejected, so a restore keeps its turn structure and crash-recovery checks: one that does not fit may use a reserve of 1/64 of the budget beyond it, with a turn error cut to at most 1 KiB from each end, and further when escaping makes that too long, and past the reserve it is kept without its error. A boundary that does not fit even then is kept outside the budget. After a save fails, a session keeps one turn of these: a later turn start drops the unsent ones from the previous turn start, and a turn end or provider exit drops an earlier one of its kind in the same turn; the dropped boundaries join the gap marker's count, though not the live loss count. Compacting only after a failed save means a store that works again saves every boundary queued with it. Once committed, these boundaries and markers no longer wait in memory for a failing directory barrier. Markers are not counted in the budget: rejections with no admitted entry between them share one marker, saved again with the new count under a fresh event key, including behind a committed marker still waiting on its directory barrier, so a crash during a long barrier failure leaves the marker's full count. Each such rejection appends one small row; a restore shows the latest copy of a marker, whose count only grows. A rejected recovery batch gets its own marker, named after the batch and counting one row per insertion plus its report. It is counted and queued once however often Retry is rejected, the writer never merges it into another marker (other markers merge past it), though a restore may show it merged with an adjacent one, and a restore drops it when a Retry saved the batch later. A restore merges markers that end up next to each other. A restore does not merge markers logged on either side of a recovery batch, so a marker the batch filled stays filled. When a crash recovery adds the provider's rows after its last match, the markers right after that match (with no other row between) are replaced through the batch with one that says the entries were not saved there and recovery has added what the provider recorded, so they no longer claim the loss; a recovery the size cap truncated fills none. Later entries are admitted again as soon as they fit, so logging is never disabled. A restored marker renders as a Partial report, like a crash-recovery report (a filled one renders without the badge), and does not change whether a recovery check runs. Quit blocks until retained writes, draft, metadata and gap markers are saved; already rejected entries never veto Quit. A log checkpoint fails only on retryable work, so a recovery batch confirms despite earlier loss. A recovery batch the budget rejects is not confirmed: the recovery card says it is not saved, Retry logs it again, and Continue lets the next message go, after which a restart may not show it. Messages cut to a quarter of the budget differ from the provider's copy, so a later recovery reports them as a conflict. Idle eviction keeps a process whose session has lost entries. There is no exit-anyway route. Permission repair must include the database, any `-wal`/`-shm` sidecars, and their parent directory: a read during a read-only period can create read-only sidecars.

SQLite depends on the filesystem and storage device honouring sync requests. It cannot recover in-memory failed writes after a forced kill, or incomplete streamed items that were never submitted for persistence. A blocked filesystem syscall can still delay Quit. Provider-native crash reconciliation is separate work.

## Import, versions and backups

The configured legacy `workspace.json` path maps to `workspace.sqlite3`; other legacy filenames get `.sqlite3` appended, while an existing SQLite header identifies a database directly. The configured path's existing lock stem is retained, so old and new desktop builds cannot run concurrently against it. On first open, one IMMEDIATE transaction creates/upgrades the schema, validates the old workspace, imports session logs in deterministic filename/line order and writes an import-complete marker. Invalid or torn legacy log lines are skipped as before. Missing and nonregular log paths are skipped, including dangling symlinks, directories and FIFOs; symlinks to regular files still import. An unreadable regular log aborts with its path rather than silently completing an incomplete import. An I/O/validation failure or process death before commit rolls the whole import back. Restart retries; after commit, changed legacy files are never imported again. Library callers must create the parent before opening Store; desktop startup already does this.

Old files remain untouched as backups, and old builds never write SQLite. Returning to an old build shows its old backup, not changes saved by the new build. Schema migrations use `PRAGMA user_version` transactionally. A schema newer than this build is refused, never downgraded.

Do not copy only the `.sqlite3` file while the app is running: a committed tail can still be in `-wal`. Use SQLite's backup API (the native verifier's snapshot does this), or quit successfully before copying the database. Keep backups private: transcripts contain user and provider text.

The event/projection transaction model takes design ideas from t3code's event sink, implemented independently in Rust. Schema version 2 adds an `accounts` projection (id, position, payload) for provider accounts, which are never written into the workspace payload; `account.upserted` and `account.removed` events record changes in the same transaction. Schema version 3 adds a `projects` projection, and schema version 4 a `prompts` projection for saved prompts. Schema version 5 adds a `deliveries` projection (child session, position, payload) for launched sessions' results; a launch writes its session and its delivery in one transaction, and each state change appends a `delivery.upserted` event. Deliveries are never written into the workspace payload or removed (see `docs/design/orchestrator.md`). Schema version 6 adds a `notes` projection (project folder, position, payload) holding each project's note; every change appends `note.upserted`, and emptying a note removes its row with `note.removed`. Idempotency records and client cursors are not stored yet.

## Attached images

An image attached to a draft is copied into `attachments/` beside the workspace database, named by the SHA-256 of its bytes and the extension of its type (`<sha256>.png`, `.jpg`, `.gif` or `.webp`), so the same image is stored once and survives the original moving or changing. The copy is written to a hidden temporary file of its own, synced, renamed into place and its folder synced, so a crash never leaves a half-written image under a final name. Copies are written one at a time, and never while the retention sweep runs. The type is read from the file's first bytes, not its name. Drafts (`draft_attachments` on the session) and the transcript log (`Entry::Attachments`, after the message it was sent with) hold only references: hash, media type and the name it was attached as. Sending reads the copy, so a copy deleted by hand makes Send refuse with the image's name and keep the draft.

Images over 20 MiB are refused when attached, with the size and the limit; `KEYSTONE_ATTACHMENT_MAX_MB` sets another limit in whole MiB (a value that is not a positive number keeps the default). The limit is per image; a message may carry several. Both tested provider CLIs shrink large images themselves before they reach the model (see [the image input probe](../research/image-input-probe.md)), so the limit bounds disk use and the size of each image Keystone sends rather than the model's own limit.

At startup Keystone deletes, off the UI thread, copies last attached or sent more than 30 days ago, and temporary files a crash left behind more than a day ago. A copy any session's draft holds is never deleted. Attaching or sending an image resets its age. `KEYSTONE_ATTACHMENT_KEEP_DAYS` sets another number of days, and 0 keeps copies forever; a value that is not a whole number keeps the default of 30. Attaching waits until the sweep is done, so an image attached at startup is never deleted under it. A sent message whose copy has been deleted still shows its chip in the transcript, with a file icon in place of the thumbnail.
